# ReaderWrangler: Cross-Domain Conduit — Design Plan

## Overview

The Cloudflare Workers + KV relay is the sole transfer path between the fetcher and the app. The file picker is removed from the routine import flow and retained only as an explicit backup/restore utility. This document covers the relay architecture, the deleted-ASIN exclusion list, mobile device sync, backup/restore, and app-side UX changes.

---

## The Exclusion List

The core data structure enabling permanent deletes is a **deleted-ASIN exclusion list** — a simple array of ASINs the user has purged from the Trash Bin.

```json
{
  "deletedAsins": ["B001ABC123", "B002DEF456", "B003GHI789"],
  "deletedAt": {
    "B001ABC123": "2026-02-20T14:30:00Z",
    "B002DEF456": "2026-02-18T09:15:00Z"
  }
}
```

The fetcher filters these ASINs out at import time. The app appends to this list on purge (not on delete — see Two-Stage Lifecycle below). The list is never cleared automatically.

**Canonical location:** The app's `localStorage`. The relay is a mirror, pushed on every change.

## Cloudflare Relay Architecture

A single Cloudflare Worker serves three distinct purposes:

1. **Ephemeral library transfer** — carries fetched library data from `amazon.com` to `readerwrangler.com`. Auto-expires after 24 hours, deleted by the app after successful import.
2. **Persistent exclusion list** — carries the deleted-ASIN list from the app to the fetcher. No expiration. Updated on every purge.
3. **Persistent device state** — carries the full library snapshot from desktop to mobile for read-only sync. No expiration. Updated after every successful import.

All three are scoped to the user's channel ID. The worker only ever sees ciphertext.

### KV Key Layout

```
relay:{channelId}:manifest          → upload manifest (TTL: 24h)
relay:{channelId}:chunk:{n}         → encrypted compressed library data (TTL: 24h)
relay:{channelId}:exclusions        → encrypted exclusion list (NO TTL — persistent)
relay:{channelId}:device-state      → encrypted full library snapshot (NO TTL — persistent)
```

### Worker Endpoints

```
POST   /upload/{channelId}/chunk/{n}    Upload a library data chunk
POST   /upload/{channelId}/manifest     Signal upload complete
GET    /status/{channelId}              Check if library data is available
GET    /download/{channelId}/chunk/{n}  Download a library data chunk
DELETE /cleanup/{channelId}             Delete all ephemeral keys (called after successful import)

PUT    /exclusions/{channelId}          Update the exclusion list (called by app on purge)
GET    /exclusions/{channelId}          Fetch the exclusion list (called by fetcher on run)

PUT    /device-state/{channelId}        Update full library snapshot (called by app after import)
GET    /device-state/{channelId}        Fetch full library snapshot (called by mobile on open)
```

### Security Model

**Channel ID** — UUID generated by the app on first setup. Acts as the access token for all KV operations. 122 bits of entropy; unguessable without brute force.

**Passphrase** — Random 32-character string generated by the bookmarklet installation page at setup time. Baked into the bookmarklet code as a literal. Stored in the app's localStorage. Used as the AES-256-GCM key for all data passing through the relay. The worker only ever sees ciphertext.

**CORS lockdown** — Worker only accepts requests from `https://www.amazon.com`, `https://readerwrangler.com`, and `http://localhost` (dev only).

### Passphrase Bootstrap

1. User visits ReaderWrangler Settings → Relay Setup
2. App generates a channel ID (UUID) and a passphrase (random 32-char string)
3. App stores both in its own localStorage
4. App dynamically generates the bookmarklet code with channel ID and passphrase baked in as literals
5. User drags the generated bookmarklet link to their toolbar — done

The passphrase never appears in a URL, never transits the relay, and exists only in the app's localStorage and the bookmarklet code itself.

## Data Flows

### Library Transfer (Fetcher → App)

```
amazon.com (bookmarklet)          Cloudflare Worker           readerwrangler.com
       |                                                               |
       | 1. Fetch library from Amazon                                  |
       | 2. GET /exclusions/{channelId} ──────────────────────────>    |
       | 3. Decrypt exclusion list, filter ASINs                       |
       | 4. Compress + encrypt filtered JSON                           |
       | 5. POST /upload/chunk/0 ─────────────────────────────────>    |
       | 6. POST /upload/manifest ────────────────────────────────>    |
       |                                                               |
       |                          <──────── GET /status/{channelId} ── |
       |                          ──── "ready" ──────────────────────> |
       |                          <──────── GET /download/chunk/0 ──── |
       |                          ──── chunk data ────────────────────>|
       |                          <──────── DELETE /cleanup ────────── |
       |                          ──── 200 OK ────────────────────────>|
       |                                                               |
       |                                        Decrypt, decompress,   |
       |                                        merge into app state,  |
       |                                        PUT /device-state      |
```

After a successful import the app pushes the updated library snapshot to `device-state` so mobile is always current.

### Delete Sync (App → Fetcher)

```
readerwrangler.com                 Cloudflare Worker         amazon.com (next run)
       |                                                            |
       | User purges from Trash                                     |
       | Append ASIN to local exclusion list                        |
       | Encrypt exclusion list                                     |
       | PUT /exclusions/{channelId} ─────────────────────────>     |
       |                                                            |
       |                                        GET /exclusions ─── |
       |                                        ──── ciphertext ──> |
       |                                        Decrypt, filter     |
       |                                        (deleted book       |
       |                                         not imported)      |
```

### Mobile Sync (Desktop → Mobile)

```
readerwrangler.com (desktop)      Cloudflare Worker      readerwrangler.com (mobile)
       |                                                            |
       | After every successful import:                             |
       | Encrypt full library state                                 |
       | PUT /device-state/{channelId} ──────────────────────>      |
       |                                                            |
       |                                        On app open: ────── |
       |                                        GET /device-state ─ |
       |                                        Decrypt, load state |
```

Mobile is read-only. No write-back, no conflict resolution. Desktop is always the source of truth.

## Mobile Device Pairing

Pairing a mobile device reuses the existing credentials (channel ID + passphrase). The user needs to transfer both values to their phone without typing them manually.

**QR code pairing (recommended):**

1. Desktop Settings → "Add Mobile Device" → shows QR code encoding `{channelId}:{passphrase}`
2. User scans QR code with phone camera
3. ReaderWrangler opens on mobile, reads credentials from URL fragment, stores in mobile localStorage, clears from URL
4. Mobile immediately fetches `device-state` and loads library — done

The credentials are in the URL fragment only for a fraction of a second during the handoff. Fragment content is never sent to any server.

**Manual pairing (fallback):** Settings → "Show Credentials" displays channel ID and passphrase as copyable text for users who prefer to transfer them another way (e.g. password manager).

## Chunking & Compression

Book metadata JSON is highly repetitive and compresses well using the browser's native `CompressionStream` (gzip):

| Library Size | Raw JSON | Compressed | Chunks Needed |
|---|---|---|---|
| 2,500 books | ~42 MB | ~5–8 MB | 1 |
| 5,000 books | ~84 MB | ~10–16 MB | 1 |
| 10,000 books | ~168 MB | ~20–32 MB | 1–2 |

Cloudflare KV free tier supports 25 MB per value. At current library sizes a single chunk after compression is well within limits. The chunking infrastructure exists for future growth.

### Manifest Schema

```json
{
  "channelId": "a1b2c3d4-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "chunkCount": 1,
  "totalBytes": 43827200,
  "compressedBytes": 6291456,
  "timestamp": "2026-02-27T12:00:00Z",
  "checksum": "sha256:abc123...",
  "encrypted": true,
  "bookCount": 2347
}
```

### Cloudflare Free Tier

| Resource | Free Limit | Expected Usage |
|---|---|---|
| Worker requests | 100,000/day | ~5–10 per user per import |
| KV reads | 100,000/day | Low |
| KV writes | 1,000/day | Low |
| KV storage | 1 GB | Negligible |

For hundreds of users doing occasional imports, free tier is more than sufficient.

## Delete UX — Two-Stage Lifecycle

Deleting a book is a two-stage process. The exclusion list is only updated at Stage 2 (purge), not Stage 1 (delete). This is critical: adding an ASIN to the exclusion list too early would prevent recovery.

**Stage 1 — Delete (soft)**
- User selects "Delete" from book context menu or detail view
- No confirmation dialog needed — Trash Bin is the safety net
- Book moves to Trash Bin immediately, disappears from all normal views
- ASIN is NOT yet added to the exclusion list
- If the fetcher runs while a book is in Trash, it will still be imported — app reconciles by leaving it in Trash rather than restoring it to the library

**Stage 2 — Purge (hard)**
- Triggered manually ("Empty Trash" or per-book "Delete Permanently") or automatically after configured period (default: 30 days)
- ASIN is added to the exclusion list in localStorage
- Exclusion list pushed to relay in background, silently
- Book is unrecoverable from this point forward

**Trash Bin behavior:**
- Accessible as a system view (not a user-created folder)
- Shows book title, cover, date deleted, days until auto-purge
- Per-book actions: Restore, Delete Permanently
- Global actions: Empty Trash, configure auto-purge period
- Restored books return to their previous folder/collection if it still exists, otherwise return to the default library view

**Edge case — book restored then re-deleted:**
No special handling needed. Restore simply removes it from Trash; a subsequent delete moves it back to Trash as normal. The ASIN never hits the exclusion list until a purge occurs.

**Edge case — book in Trash is fetched again:**
The fetcher imports it (it's not on the exclusion list yet). The app detects the ASIN exists in Trash and leaves it there rather than creating a duplicate in the library. The "deleted on" timestamp and auto-purge countdown are preserved.

## Wishlist Duplicate Detection

The most common delete scenario — wishlist books that duplicate owned books — is handled automatically on import, not through the manual delete → trash → purge flow.

**Behavior:** When the app imports data, it compares each wishlist book's ASIN against the set of owned book ASINs. Any wishlist entry whose ASIN matches an owned book is automatically suppressed — never added to the library.

This is deterministic and safe: an owned book always takes precedence over a wishlist entry for the same ASIN. No user interaction required. No Trash Bin involvement.

**Scope:** This only applies to the owned-vs-wishlist duplicate case. It does not affect books the user manually deletes for other reasons (those go through the Trash Bin flow).

### Three Layers of Duplicate Handling

**Layer 1 — Automatic on import:** Wishlist entries whose ASIN matches an owned book are silently suppressed. Prevents new duplicates from entering.

**Layer 2 — On-demand per folder:** Right-click a folder → "Remove Wishlist Duplicates." Scans that folder for wishlist entries matching owned ASINs and silently removes them. Toast: "Removed N wishlist duplicates."

**Layer 3 — One-time global cleanup:** Tools menu → "Remove All Wishlist Duplicates." Same scan across the entire library. Use case: initial cleanup of a library with years of accumulated duplicates.

**Disposition:** Removed duplicates are silently suppressed — they do not go to Trash. These are data artifacts (provably redundant wishlist entries for books the user owns), not user-initiated deletes.

**Implementation:** All three layers use the same core filter:

```javascript
const ownedAsins = new Set(ownedBooks.map(b => b.asin));
const filteredWishlist = wishlistBooks.filter(b => !ownedAsins.has(b.asin));
```

Layer 1 runs during import. Layers 2 and 3 run on the current app state.

## Trash Bin — UI Placement

**Location:** Fixed at the bottom of the left pane, below all user folders and tag views. Separated from the folder/tag list by a subtle divider line. Not draggable, not reorderable.

**Rationale:** Trash is a holding area, not a browsing destination. The bottom-of-sidebar placement follows the convention used by macOS Finder, Windows Explorer, Gmail, and Google Drive.

**Badge:** Shows a count when non-empty — e.g., "Trash (3)" — so users can see at a glance whether cleanup is pending.

**Discoverability for long folder lists:** With 200+ top-level folders, Trash may require significant scrolling. Mitigations:
- File menu → "Open Trash" as a shortcut (always accessible without scrolling)
- Keyboard shortcut (TBD — e.g., `Ctrl+Shift+Delete` or similar)
- Left pane "Collapse All" reduces top-level folder count, bringing Trash into view

**Appearance:** Muted styling when empty (gray icon + text), standard styling when non-empty. SVG trash icon preferred over emoji (emoji cannot be recolored for dark mode).

## Settings Page

### Relay Setup (first-time)
- Generates channel ID and passphrase
- Displays personalized bookmarklet drag link
- Step-by-step setup instructions
- Privacy disclosure: "Your library data is encrypted before leaving your browser and automatically deleted from the relay after import. Cloudflare never sees your data in plaintext."

### Relay Management (after setup)
- Relay status: last sync time, connection health
- "Add Mobile Device" → shows QR code for pairing
- "Show Credentials" → displays channel ID and passphrase for manual transfer
- "Regenerate Credentials" → invalidates old bookmarklet, requires reinstall (destructive action, confirmation required)

### Backup & Restore
- "Export Backup" → downloads full library JSON including exclusion list and relay credentials (channel ID + passphrase). Always includes credentials — no user choice. On click, displays a disclosure dialog before download:

  > **This backup contains sensitive credentials**
  > This file includes your relay credentials. Anyone with this file can access your encrypted relay data. Store it somewhere secure — the same place you'd store a password.
  > [Download Backup] [Cancel]

- "Import Backup" → file picker, restores full library state and credentials from a previously exported backup. If credentials are present in the backup, they replace the current credentials and the user is reminded to reinstall the bookmarklet and re-pair any mobile devices.
- Note: Import Backup is for disaster recovery only, not routine use. Routine phone setup uses QR code pairing.

## Bookmarklet Changes

- Channel ID and passphrase baked in at install time
- On run:
  1. Fetch exclusion list from relay, decrypt, build filter set
  2. Fetch Amazon library
  3. Filter deleted ASINs
  4. Compress, encrypt, upload chunks to relay
  5. Post manifest to signal completion
- User experience: click bookmarklet → progress indicator → done. No file dialogs.

---

## Rollout

1. Ship Cloudflare relay as the default experience from day one — no file-picker path in the main flow
2. Ship backup export/import as a settings utility
3. Ship mobile QR pairing alongside or shortly after initial relay launch
