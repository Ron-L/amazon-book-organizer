## 🎯 What Worked Well

### 1. **Single-alpha release**
- The entire feature (dialog toggle, bulk edit, storage.js merge protection, undo/redo) shipped in one alpha with zero rework
- Plan mode identified all touch points upfront; no surprises during implementation
- **Lesson**: For features that extend existing patterns (bulk edit modal, userEdited flags), plan mode + established patterns = first-try success

### 2. **User-driven root cause analysis**
- User investigated the Amazon data gap methodically: deleted the book, re-fetched, checked multiple ASINs, traced the `hasOwnership` DOM class failure
- Identified that Amazon's library API doesn't return certain owned books despite them showing as "Read Now" on Amazon
- This turned what could have been a complex fetcher bug investigation into a clear UX problem with a simple solution
- **Lesson**: When data flows through multiple systems (Amazon API → fetcher → JSON → app), the user is often the best debugger of the external system boundaries

### 3. **Reuse of v5.4.7 infrastructure**
- `userEdited` flags, `saveBulkEdit()` field mapping, `openBulkEditModal()` field routing, and undo/redo patterns all extended naturally
- The ownership toggle added only ~95 net lines despite touching dialog, bulk edit, context menu, storage.js merge, and undo/redo

## 📚 Lessons Learned

### 1. **Boolean fields need special handling in the bulk edit pattern**
- The bulk edit system was designed for string/number fields. Boolean fields (onWishlist) required:
  - String-to-boolean conversion in `saveBulkEdit()` (`bulkEditInput === 'true'`)
  - A toggle button UI variant instead of a text input
  - Companion field derivation (`ownershipType` derived from `onWishlist`) in save, undo, and redo
- The pattern is now established for any future boolean fields in bulk edit

### 2. **Companion fields (onWishlist + ownershipType) should be tracked by a single userEdited flag**
- `ownershipType` is always derived from `onWishlist`, so only `userEdited.onWishlist` is needed
- The `ownershipType` key is filtered out of the `userEdited` flags (alongside `userNote`) to avoid redundancy
- Pattern: when two fields always change together, track with one flag and derive the other

### 3. **Amazon API data gaps are a real user problem**
- Amazon's library API doesn't return all owned books — some books show as "Read Now" on Amazon but aren't in the library fetch
- The `hasOwnership` DOM class on series pages is also unreliable
- Users need manual override capabilities for any Amazon-sourced metadata that could be wrong
- This validates the broader `userEdited` architecture — it's not just for typo fixes, it's for correcting data gaps

## Final Thoughts

This was a clean, fast release that demonstrated the compound value of the v5.4.7 infrastructure. The `userEdited` flag system, bulk edit modal pattern, and storage.js merge protection all extended naturally to support ownership toggling. The real insight was the user's discovery that Amazon's library API has data gaps — books can show as owned on Amazon's UI but not appear in the API response. This makes manual override capabilities essential, not just nice-to-have.

**Key Takeaway**: When your app depends on external data sources, always give users the ability to override any imported field — the source data will inevitably be wrong for some users.
