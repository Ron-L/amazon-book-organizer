## 🎯 What Worked Well

### 1. **Two-phase design structure**
- Phase 1 (dialog edit mode) and Phase 2 (bulk edit context menu) were cleanly separated
- Phase 1 established the patterns (combobox, ESC chain, undo/redo) that Phase 2 directly reused
- The bulk edit modal was essentially a simplified version of the dialog edit mode
- **Lesson**: When building related features, sequence them so the first establishes reusable patterns for the second

### 2. **Plan mode for Phase 2**
- Creating the detailed plan before coding Phase 2 produced a clean single-alpha implementation (alpha.1)
- All context menu integration, modal JSX, undo/redo, and ESC handling worked on first test
- Contrast with Phase 1's 10 alphas where the series dropdown ESC chain required 4 iterations
- **Lesson**: Upfront planning with line-number references and pattern identification pays off in fewer iterations

### 3. **`userEdited` flag architecture**
- User-initiated discovery that Amazon re-imports overwrite edits led to an elegant solution
- Using `!!book.userEdited` as the signal to distinguish backup vs Amazon imports is simple and robust — backups carry the flag, Amazon data doesn't
- Required no new state, no new parameters, and no UI changes
- **Lesson**: Signals embedded in the data itself are cleaner than out-of-band parameters

### 4. **Diagnostic-driven debugging**
- When the user reported `userEdited` wasn't working, targeted `console.log` in the merge path proved the code was correct
- The real issue was a stale `storage.js` cache buster — would have been hours of unnecessary investigation without diagnostics
- **Lesson**: Strategic diagnostic logging in data transformation paths saves debugging time

## ❌ Mistakes Made

### 1. **Series dropdown ESC chain — 4 alpha iterations (alpha.7-10)**
- React `stopPropagation()` on the chevron button blocked ESC from reaching the global `window.addEventListener` handler
- This is a known pattern (documented in MEMORY.md) but wasn't applied proactively
- Each iteration fixed one layer: dependency array → chevron onKeyDown → focus trap → full layered chain
- **Fix**: The layered ESC pattern (dropdown → input → cancel) should have been the starting design. Cost: 3 unnecessary alpha cycles

### 2. **Stale cache buster on storage.js**
- The `?v=` query parameter for `storage.js` was stuck at `5.0.0` while the app was at `5.4.7`
- Browser served stale code that lacked the `userEdited` merge logic, even after the code was committed
- Hard to diagnose because the JS file itself was correct — just not being served
- **Fix**: Updated to `?v=5.4.7`. Future prevention: use dynamic `APP_VERSION` constant for all script cache busters

### 3. **False failure report due to filter reset**
- After Amazon import, the filter resets to show all books
- User initially thought edits were overwritten, but was actually looking at different books
- Diagnostic logging proved the merge was working correctly
- **Fix**: No code fix needed — awareness item. The diagnostic logging was the mitigation

## 📚 Lessons Learned

### 1. **Design ESC chains as layered systems from the start**
- When a component has nested dismissible elements (dropdown inside a modal, or dropdown inside an edit mode), design the full ESC chain upfront: innermost → next → outermost
- Don't add layers reactively — that's how you get 4 alpha iterations for something that should take 1
- The layered pattern from alpha.10 should be the starting template for all future comboboxes
- Pattern: `ESC with dropdown open → close dropdown, focus input` → `ESC with input focused → blur input` → `ESC reaches global handler → cancel edit mode`

### 2. **Cache busters must track a single source of truth**
- `storage.js` and `uiHelpers.js` had manually-maintained `?v=` values in `readerwrangler.html`
- These fell out of sync while `APP_VERSION` was correctly updated
- The `APP_VERSION` constant already exists as the single source — module scripts should use it too
- Currently partially done: main app script uses it dynamically, module scripts use hardcoded values

### 3. **Distinguish "merge" from "restore" in import logic**
- Amazon imports are a *merge* (combine new data with existing user edits)
- Backup imports are a *restore* (replace with snapshot)
- Using a signal on the data itself (`!!book.userEdited`) to distinguish these is cleaner than adding parameters or flags to the import function
- Why this matters: the same `saveBooksToIndexedDB()` code path handles both cases, but they have fundamentally different semantics

### 4. **Diagnostic logging has production value**
- The `🛡️ Preserving user-edited fields` log was originally added for debugging but proved valuable enough to keep
- It fires only when the merge logic actively protects a field — zero-noise in normal operation
- Targeted, conditional logging > blanket verbose logging

## 🤖 AI Collaboration Insights

### Practices That Required User Prompting
- **`userEdited` feature itself**: User discovered during testing that Amazon re-imports overwrite edits — not anticipated during planning. AI didn't foresee this data integrity issue
- **Backup vs Amazon distinction**: User correctly identified that backup restore should be a true snapshot, not honor existing IndexedDB flags. AI's initial implementation treated both import types identically
- **"Pause for discussion"**: User explicitly requested this when debugging was going in circles. The pause led to the user providing evidence (backup file inspection) that narrowed the root cause to the code-serving layer, not the code itself

### What Ground Rules Helped
- **CLAUDE.md commit-before-test rule**: Each of 15 alphas was committed, making the evolution easy to track and revert if needed
- **Stop and ask before acting**: Prevented premature "fixes" during the false failure report — discussion revealed the real issue was filter reset, not data loss
- **Plan mode**: The Phase 2 plan with specific line numbers and pattern references enabled a single-alpha implementation

## Final Thoughts

This was a substantial release combining two related features (dialog edit + bulk edit) with an emergent third feature (`userEdited` protection) that wasn't in the original plan. The `userEdited` discovery demonstrates the value of testing end-to-end workflows — editing a field and *then* re-importing exposed a data integrity issue that unit-level thinking would have missed. The cleanest win was the backup/Amazon distinction using `!!book.userEdited` as the signal — zero new infrastructure, just a conditional check on existing data.

**Key Takeaway**: Design import logic as two distinct operations from the start — *merge* (combine with existing) vs *restore* (replace with snapshot) — because they have fundamentally different semantics even when they share the same code path.
