# v6.16.0 Release Post-Mortem (Auto-Organize live preview + convergence)

**Date**: 2026-08-10
**Duration**: multi-session (long-running branch `feature/book-nav-filter`)
**Versions Iterated**: ~30 alpha iterations (6.16.0-alpha.1 → alpha.30)
**Release**: prod + dev, commit `bd328d5`, **clean fast-forward** (both remotes were still at 6.15.0 `2173f0a` — no divergence, no reconcile)

---

## 🎯 What Worked Well

### 1. **Build a reusable primitive once, then converge onto it**
The right-click Auto-Organize preview was built first (already-filed flow → checkbox tree → unified selection → destination context). When the wizard needed the same power, we didn't rebuild — we extracted `openAutoOrgPreviewCore(authorGroups, srcId, opts, mode, label)` and pointed **both** paths at it. The wizard collapsed to a pure author-picker. One preview component now serves two entry points, and every later feature (mode toggle, live Options, full-neighborhood) landed in **both** paths for free.

### 2. **"Handle the state gracefully" beat "forbid the state" — every time**
The recurring UX principle this release: when something's ambiguous or unusual, **surface it and let the user decide**, don't prevent it. Applied to: the Inbox+folder+list triple-membership (surfaced "already filed" + remove-from-Inbox instead of a forced invariant); the "already at destination" case; the incomplete-series organize. Ron pushed hard on this ("RW is flexible like a file explorer; don't force a workflow"), and he was right each time.

### 3. **Direct manipulation > configure-then-preview**
Moving the mode (By Author/By Series) and the series options into the **live preview** — where you see the folders regroup as you change them — was Ron's idea and it's the single biggest UX win of the release. It also resolved the wizard/right-click asymmetry by making the preview the one control surface.

### 4. **Pure engine + unit tests caught and locked real bugs**
Three correctness bugs were caught by (or locked in with) the node test suite: the **SEQUENCE_SERIES redo** re-deriving 1..N (would wipe explicit numbers), and the **existing-series-folder split** (threshold scattered a series that already had a home). The engine's purity made the fix + a regression test trivial (12 tests, all green).

### 5. **Ron's domain intuition repeatedly sharpened the design**
The best calls originated or got corrected by Ron: the wizard should **act on what's shown** (not the full selection); the preview should show the **whole author folder**, not just the target; the small "already here" covers shouldn't be **grayed** (collides with wishlist); the mode belongs in the preview; the options should live there too. Capturing these in code + this PM is the durable payoff.

## ❌ Mistakes Made

### 1. **Over-recommended / over-engineered several UX calls that Ron then vetoed**
- **The "Inbox can't co-hold a filed book" invariant (C)** — I proposed a forced rule; Ron rejected it as over-restrictive. Correct — we handled it gracefully instead.
- **The ghost/borderless Cancel** — I removed the button's fill to disambiguate; it just made it look un-clickable. Reverted.
- **⊘-on-excluded covers** — I wanted to mark the excluded (minority); Ron pushed for the conventional "mark the selected," and he was right (⊘ reads as "forbidden").
- **Wizard filter as view-only** — I built it as a pure find tool; Ron wanted the action to operate on what's *shown*, which is the more natural single-author flow.

Pattern: my *first* instinct optimized for consistency/edge-cases; Ron's optimized for the common workflow, and the common workflow usually won. **Lesson reinforced: present options, recommend, and defer to the user's workflow read on UX.**

### 2. **"Minor" kept becoming "major"**
Several batches pitched as small (the already-filed flow, "make the wizard match") each spawned multi-alpha efforts (checkbox tree, unified selection, convergence, Stage 1/2 options migration). 30 alphas. Ron was on board at each step, but the framing was repeatedly optimistic.

### 3. **A controlled number input with a snapback**
The threshold field snapped back on backspace (classic controlled-input trap) and doubled the native spinners with my −/+. Took a Ron nudge to extract a proper `ThresholdStepper` with its own edit state.

## 📚 Lessons Learned

1. **On UX, the user's workflow beats the assistant's consistency instinct** — surface options, don't over-prescribe. (The C invariant, the wizard-filter semantics, ⊘-vs-✓.)
2. **Handle gracefully, don't forbid** — for a deliberately flexible tool, surfacing an odd state + an escape hatch is almost always better than a guard.
3. **Converge onto one component** — two ways into the same operation should share the same confirm/preview surface; extract the core early.
4. **The preview should mirror the engine exactly** — every time the display bucketed differently from `computeOrganizePlan` (threshold, misc, existing-folder override) it was a bug; keep them in lockstep.
5. **Persist what the user tunes** — options that don't stick ("set 1, cancelled, reverted to 33") are a trust bug; write live changes back to the shared, persisted default.

## 🤖 AI Collaboration Insights

### What Worked
- **Deep, iterative design dialogue.** Nearly every decision (mode toggle, live options, neighborhood view, shelf nav, wizard semantics) was reasoned *with* Ron across alphas, with browser testing between each — the only way to catch the JSX/interaction issues locally-untestable code hides.
- **Committing an alpha before every test** kept a clean, revertible trail across 30 iterations.

### Friction
- **No local browser test** (in-browser Babel/JSX) means every UI change is verified by Ron. I leaned on careful read-back + engine unit tests, but interaction bugs (snapback, redundant spinners, the wizard-preview stacking) surfaced only in his testing.
- **A 945-line diff on one ~17k-line file** — batch-editing a giant file remains error-prone; re-reading before each edit was the mitigation.

## Final Thoughts
This started as "#40 + #55" and became a ground-up rethink of Auto-Organize into a single live workspace — because we kept following the *right* principle instead of the tactical patch: handle-don't-forbid, one-preview-for-everything, tune-against-the-result, and the-user's-workflow-wins. The engine's purity + tests caught the correctness bugs; Ron's UX instinct caught the interaction ones. The result is coherent in a way the two separate paths never were.

**Key Takeaway**: When two features do the same thing, converge them onto one surface — and when in doubt on UX, build the option the *common workflow* wants, not the one that's tidiest in the abstract.
