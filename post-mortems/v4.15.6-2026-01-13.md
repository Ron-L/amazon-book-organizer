## What Worked Well

### 1. **UX Expert Persona**
- User asked Claude to "put on UX expert hat" before making design decisions
- Led to better choice: inline expansion vs modal for Custom dates
- Reasoning: context preservation, fewer clicks, progressive disclosure
- **Lesson**: Explicitly invoking a persona produces more thoughtful domain-specific recommendations

### 2. **Instrumentation Over Guessing**
- User emphasized: "I prefer that rather than guessing about causes, race conditions, etc. that we instrument the code and gather evidence"
- Added console.log statements at key points in load/save/effect cycle
- Evidence clearly showed: datePreset effect firing with initial empty state BEFORE load effect completed
- Root cause identified in minutes, not hours
- **Lesson**: Debug logging reveals execution order that reasoning alone can miss

### 3. **Incremental Commits**
- 13 letter versions allowed precise rollback points
- Each commit focused on single concern (UI, logic, persistence, bug fix)
- Made it easy to identify which change introduced issues
- **Lesson**: Small commits during development pay off during debugging

## Mistakes Made

### 1. **Race Condition Between Effects**
- Initial implementation had datePreset useEffect that cleared dates when preset was ''
- This effect ran during initial render BEFORE the load effect populated values
- Result: dates loaded correctly then immediately cleared
- **Fix**: Added `filtersLoadedRef` pattern - skip effect until load completes (100ms timeout)

### 2. **Active Filters Banner Using Wrong State**
- Banner checked `dateFrom || dateTo` instead of `datePreset`
- Worked for Custom (which sets dates) but not for presets (which compute dates)
- User caught this in testing: "Active filters does not show" for presets
- **Fix**: Changed banner to check `datePreset` and display friendly names

## Lessons Learned

### 1. **React useEffect Ordering is Non-Deterministic**
- Multiple useEffects with `[]` dependency don't have guaranteed order
- Initial state values trigger effects before load effects complete
- Pattern: Use a ref to gate effects that depend on loaded data
```javascript
const filtersLoadedRef = useRef(false);

// Load effect
useEffect(() => {
    // ... load from localStorage ...
    setTimeout(() => { filtersLoadedRef.current = true; }, 100);
}, []);

// Dependent effect
useEffect(() => {
    if (!filtersLoadedRef.current) return; // Skip during load
    // ... rest of effect ...
}, [dependency]);
```

### 2. **Filter Count Should Match User Mental Model**
- User sees "Date: Last 30 Days" as ONE filter, not two (dateFrom + dateTo)
- Original implementation counted dateFrom and dateTo separately = showed "2"
- Fix: Count datePreset as 1 filter
- **Lesson**: UI counts should reflect user's perception, not internal data structure

## Final Thoughts

Clean feature implementation with one significant bug (race condition) discovered and fixed through instrumentation. The user's insistence on "evidence over guessing" was the key to fast debugging - console logs immediately revealed the effect firing order issue that would have taken much longer to reason through.

**Key Takeaway**: When debugging React state issues, add console.log statements to show WHEN effects fire, not just WHAT values are - execution order is often the culprit.
