## What Happened

### The Problem

User discovered overlapping columns in List view:
- Rating and Series columns overlaid
- My Ratings and Date Added columns overlaid

Inspection revealed CSS: `style="width: var(--col-series, nullpx);"`

### Root Cause

**localStorage contained null column widths that became invalid CSS.**

User's localStorage had:
```javascript
columnWidths: {
    "series": null,
    "seriesNum": null,
    // ... other columns with valid values
}
```

When applied to CSS custom properties, null becomes the string `"nullpx"` which is invalid. Invalid width → column has no width → columns overlay.

**Why were there nulls?** Likely from a previous version or interrupted state change. The app wasn't sanitizing null values on load or save.

### The Fix

**Phase 1 - Basic Sanitization** (commit ca5ddd3, then 47c3dfb):
Added null filtering in 4 locations:
1. Load from localStorage (line ~1145)
2. Restore from backup (line ~3382)
3. Save to localStorage (line ~1336)
4. Export to backup (line ~2712)

Pattern: `value ?? defaultWidths[key]`

**Phase 2 - Future-Proofing** (user's critical insight):

User asked: "If we add a new column, what will happen?"

**Problem identified**: Code was iterating over localStorage keys:
```javascript
Object.entries(explorerData.columnWidths).map(([key, value]) => ...)
```

This only processes columns that EXIST in localStorage. New columns added to code wouldn't appear for existing users!

**Solution**: Iterate over default keys instead:
```javascript
Object.keys(defaultWidths).map(key => [
    key,
    explorerData.columnWidths[key] ?? defaultWidths[key]
])
```

**Phase 3 - Pattern Consistency** (final amendment):

Updated save/export to match load/restore pattern for consistency and defense-in-depth.

## Lessons Learned

### 1. **Iterate Over Defaults, Not Persisted Data**

When merging localStorage with defaults, always iterate over the defaults:

```javascript
// ❌ WRONG - misses new columns
Object.entries(savedData).map(([key, value]) => ...)

// ✅ RIGHT - includes all current columns
Object.keys(defaults).map(key => savedData[key] ?? defaults[key])
```

This ensures:
- New columns automatically included
- Removed columns don't persist
- localStorage missing a column still works

### 2. **Defense-in-Depth for Data Persistence**

Sanitize at ALL boundaries:
- **Load**: Sanitize incoming data (localStorage, backup restore)
- **Save**: Sanitize outgoing data (localStorage save, backup export)

This protects against:
- Corrupted localStorage
- Race conditions
- Future code changes
- Manual localStorage edits

### 3. **Ask "What If?" Questions**

User's question "If we add a new column, what will happen?" caught a critical bug. Always consider:
- What if we add a field?
- What if we remove a field?
- What if the data is corrupted?
- What if we downgrade versions?

### 4. **Test Persistence Edge Cases**

When adding new persisted state:
- Test with missing keys
- Test with null/undefined values
- Test with extra keys (forward compatibility)
- Test with corrupt data

After context compaction or session restart, read CLAUDE.md and follow collaboration rules strictly. Don't assume permission carries over from previous session.

## Technical Details

**CSS Custom Properties with Invalid Values:**

```css
/* This in CSS: */
width: var(--col-series, nullpx);

/* Becomes this when --col-series is undefined: */
width: nullpx;  /* Invalid → ignored → no width → overlay */
```

**Why "nullpx"?**
JavaScript `null` coerced to string becomes `"null"`, concatenated with `"px"` → `"nullpx"`

**The Fix:**
```javascript
// Before concatenation, ensure value is not null:
const width = columnWidths[col] ?? defaultWidths[col] ?? 100;
style.setProperty(`--col-${col}`, `${width}px`);
```
