## What Happened

### The Problem

**Use case:** Mobile users cannot access browser dev tools to clear corrupted localStorage/IndexedDB when app won't load.

**Trigger scenarios:**
- Corrupted state prevents app initialization
- Migration errors from version upgrades
- Quota exceeded errors
- Testing/development fresh start needs

**Existing solution limitations:**
- File → Reset App requires app to load (catch-22)
- Dev tools not available on mobile devices
- Manual localStorage clearing requires technical knowledge

### The Solution

**Created standalone emergency reset page:**

**Architecture:**
- reset.html - Standalone page (works independently of main app)
- reset.js - Clear all storage and redirect
- Link from index.html footer (escape hatch when main app broken)

**UX decisions:**

1. **Styling: Tailwind CSS from CDN**
   - Visual consistency with main app
   - Minimal effort (just CDN link)
   - Professional appearance even for emergency page

2. **Confirmation: Warning page + browser confirm()**
   - Page displays prominent red warning box
   - Click "Reset App" → triggers browser confirm() dialog
   - Two-step prevents accidental resets
   - Browser-native confirm works everywhere (mobile friendly)

3. **Link placement: Landing page footer**
   - Primary use case: app won't load → user goes to landing page
   - Unintrusive gray text: "Having trouble? Emergency Reset"
   - Not in main app (defeats purpose if app broken)

**UX text iteration:**

**Initial draft issues:**
- Said "permanently delete" (inaccurate - backups exist)
- Unclear about recovery paths (backup vs library file)
- Read like sequential steps instead of alternatives

**Revised approach:**
- "Clears data from your browser" (accurate)
- Arrow format: "Import X → Get Y" (clear alternatives)
- Spells out what "organization" means (folders, tags, notes, order, price goals)
- Distinguishes two recovery scenarios:
  - Import backup → Everything (books + organization)
  - Import amazon-library.json → Books only (lose organization)

## Lessons Learned

### 1. **UX Text: Accuracy Over Panic**

**Problem:** Initial text said "permanently delete all data" but backups can restore everything.

**Impact:** Creates false panic, discourages use when actually needed.

**Better approach:**
- Be technically accurate: "Clears data from browser" not "permanently deletes"
- Lead with reassurance: "Your files on disk are safe"
- Provide actionable recovery: "Import backup → Get everything back"

**Checklist:**
```markdown
## Before writing destructive action warnings:
- [ ] Is "permanent" accurate? (Consider backups, recovery paths)
- [ ] Lead with what's safe/recoverable
- [ ] Distinguish between browser state vs disk files
- [ ] Provide clear recovery instructions
```

### 2. **UX Text: OR vs AND Clarity**

**Problem:** Recovery text read like sequential steps:
```
Recovery after reset:
• Import amazon-library.json to restore book data
• Import backup files to recover organization
```

Users might think: "Do I need to do both?"

**Better:**
```
What you can recover:
• Import backup file → Restore EVERYTHING
• Import amazon-library.json → Restore books only
```

Arrow format makes alternatives obvious.

**Pattern:**
- Use arrows (→) for cause-effect or if-then relationships
- Use "BEST" / "OR" labels when one option superior
- Spell out tradeoffs (get X, lose Y)

### 3. **Emergency Page Architecture**

**Key insight:** Emergency recovery page must work *independently* of main app.

**Why:**
- Main app broken = can't load main app to fix main app
- Standalone page breaks dependency cycle
- Mobile devices need escape hatch (no dev tools)

**Pattern:**
```
Emergency page requirements:
- [ ] Zero dependencies on main app state
- [ ] Works with CDN resources (Tailwind)
- [ ] Mobile-friendly (no dev tools needed)
- [ ] Accessible when main domain works but app doesn't
- [ ] Link from landing page (backup entry point)
```

### 4. **Browser Confirm() Still Valuable**

**Modern UX often avoids browser dialogs, but confirm() perfect here:**

Advantages:
- ✅ Works everywhere (desktop + mobile)
- ✅ Blocks until user responds (prevents accidents)
- ✅ Familiar pattern users trust
- ✅ No additional JavaScript complexity
- ✅ Can't accidentally click through

**Use when:**
- Destructive action (data loss)
- Mobile compatibility required
- Simple yes/no decision
- No complex UI needed

### 5. **Unintrusive Escape Hatches**

**Placement decision:** Footer link, gray text, small font.

**Why this works:**
- Doesn't clutter main UI
- Discoverable when needed (user reads footer when stuck)
- Professional appearance (not alarming)
- Doesn't suggest app is unstable

**Pattern:**
```
Emergency features placement:
- [ ] Accessible but not prominent
- [ ] User finds when searching for help
- [ ] Doesn't imply instability to casual visitors
- [ ] Clear label when noticed ("Emergency Reset")
```

### Recovery Instructions

**reset.html "Good News" box:**
```
Good news: This only clears data from your browser.
Your files on disk are safe.

What you can recover:
• Import backup file → Restore EVERYTHING
  (books + folders + tags + notes + order + price goals)
• Import amazon-library.json → Restore books only
  (lose folders, tags, notes, order, price goals)
```

**Browser confirm() dialog:**
```
⚠️ This will clear all ReaderWrangler data from your browser.

Your files on disk are safe. To recover:
• Import backup file → Books + organization
• Import amazon-library.json → Books only

Continue with reset?
```

**Key differences:**
- HTML box: Detailed (spells out organization components)
- Browser confirm: Concise (users skip long confirms)
- Both: Arrow format shows alternatives clearly

### Success Flow

1. User clicks "Reset App" button
2. Browser confirm() shows warning
3. User clicks OK → `performReset()` executes
4. Clear localStorage (7 keys)
5. Delete IndexedDB (ReaderWranglerDB)
6. Show success overlay with green checkmark
7. Auto-redirect after 3 seconds
8. "Go to App Now" button for immediate navigation

### Error Handling

**IndexedDB blocked state:**
```javascript
request.onblocked = () => {
    console.warn('⚠️ IndexedDB deletion blocked (close other tabs)');
    resolve(); // Resolve anyway - deletion completes when tabs close
};
```

**Why resolve on blocked:**
- User may have multiple tabs open
- Deletion completes when tabs close
- Blocking prevents success message is worse UX
- Console warning alerts developers if debugging
