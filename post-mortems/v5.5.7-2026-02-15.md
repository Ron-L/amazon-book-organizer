## 🎯 What Worked Well

### 1. **Two-phase architecture (Phase 0 → Phase 1)**
- Phase 0 converted 163 inline hex colors to 25 semantic CSS variables — zero visual change, independently valuable cleanup
- Phase 1 then only had to define dark values for those 25 variables + write Tailwind class overrides
- The separation meant Phase 0 could be tested in isolation, reducing risk of the full dark mode rollout
- **Lesson**: When a feature requires large-scale refactoring as a prerequisite, ship the refactoring as a separate testable phase before building the feature on top

### 2. **CSS ancestor-selector overrides (zero JS className changes)**
- Instead of adding `dark:` to ~1,275 className strings, used `[data-theme="dark"] .bg-white { background-color: #1e293b !important; }` in CSS
- Specificity `(0,2,0)` beats Tailwind's `(0,1,0)` naturally. Hover variants (`[data-theme="dark"] .hover\:bg-gray-50:hover`) work the same way
- ALL theme logic lives in CSS — readerwrangler.js className strings were untouched throughout Phase 1
- **Lesson**: For apps using Tailwind CDN where you can't use `dark:` in the config, CSS ancestor-selector overrides are a clean alternative that avoids touching hundreds of JSX lines

### 3. **Programmatic WCAG AA contrast check**
- Ran a systematic contrast ratio analysis of all 25 CSS variable pairings against their expected backgrounds
- Found 6 failures, 2 that mattered for functional text. Fixed by adjusting `--bg-accent` and `--text-secondary`
- Catching these programmatically was faster and more reliable than visual inspection
- **Lesson**: Run contrast checks as a discrete step after the palette is finalized but before visual testing

### 4. **Design doc upfront analysis paid off**
- DARK-MODE.md inventoried all 15 dialog backdrops, 4 context menus, 5 filter dropdowns, and categorized every surface
- The scope inventory prevented surprises during implementation — no "oh, I forgot about that modal" moments
- The estimated effort (14-22 hours in the doc) vs actual (~8-10 hours) shows the CSS override approach was more efficient than the originally planned per-element `dark:` class approach
- **Lesson**: Scope inventory for theming work is essential — enumerate every surface before starting

## ❌ Mistakes Made

### 1. **Made wrong function async after alert→dialog conversion**
- Replaced `confirm()` (synchronous) with `showConfirmDialog()` (returns Promise) requiring `await`
- Made `handleKeyDown` async, but the `await` was actually inside `handleKeyboard` — a *different* keyboard handler 400 lines later
- Babel parse error on the next test: "Unexpected reserved word 'await'" at line 2682
- Required brace-depth analysis to trace which function scope contained the await
- **Fix**: Made `handleKeyboard` async instead. Added to memory: when converting sync→async, trace the EXACT function scope containing the call, don't assume based on nearby function names

### 2. **`--bg-hover` and `--bg-elevated` set to same dark value**
- Both were `#334155` in the dark palette, making hover highlights invisible on dropdown items
- User reported "dropdowns with checkboxes don't show anything different when you hover" — the handlers were working, but the color change was invisible
- **Fix**: Changed `--bg-hover` to `#475569` (one step lighter). During palette design, verify that every pair of "base + interactive state" variables produces a visible contrast difference

### 3. **`!important` on border overrides killed drag indicator lines**
- Added `!important` to all Tailwind border-color overrides for belt-and-suspenders
- This overrode the inline JS `style.borderTop = '2px solid red'` set by drag-and-drop indicator logic
- **Fix**: Removed `!important` from border overrides — specificity `(0,2,0)` alone is sufficient vs Tailwind's `(0,1,0)`. Reserve `!important` only where specificity battles actually exist

### 4. **About dialog logo — wrong technique first**
- Tried `filter: brightness(1.5) drop-shadow()` — barely visible change
- User said "still unreadable, no appreciable change"
- Should have gone straight to `filter: invert(1) hue-rotate(180deg)` — the standard dark mode image technique
- **Fix**: Applied invert+hue-rotate. Cost one extra alpha cycle

### 5. **Tags hover used `e.target` instead of `e.currentTarget`**
- Tags dropdown items contain child elements (checkbox + span). `e.target` on `onMouseEnter` targets whichever child the mouse is over, not the parent row div
- Background change applied to the checkbox or span, not the whole row
- Collections and Series items had no hover handlers at all
- **Fix**: Changed to `e.currentTarget` which always references the element the handler is attached to. Added hover to Collections/Series. Pre-existing bug, not caused by dark mode

## 📚 Lessons Learned

### 1. **CSS `!important` and inline styles interact dangerously**
- `!important` in a stylesheet overrides inline `style={}` attributes. This is correct per CSS spec but counterintuitive
- For a codebase that mixes Tailwind classes with inline styles (drag indicators, dynamic positioning), `!important` in theme overrides is a landmine
- Rule: only use `!important` on overrides where the base Tailwind class uses `!important` itself (none in this codebase)

### 2. **Form elements need explicit dark mode styling**
- HTML `<input>`, `<textarea>`, `<select>` default to white background from the browser UA stylesheet regardless of parent styling
- A global CSS rule was needed: `[data-theme="dark"] input, textarea, select { background-color: var(--bg-input); color: var(--text-primary); }`
- This isn't obvious from a Tailwind-only perspective where you'd expect `bg-white` → dark override to catch inputs

### 3. **Emojis cannot be recolored via CSS**
- The 🪄 (magic wand) emoji was unrecognizable on dark backgrounds — dark handle blended in
- CSS `color`, `filter`, `text-shadow` don't affect emoji rendering on most platforms
- Replaced with ✨ (sparkles) which has bright tones visible on any background
- Rule: when choosing emojis for UI labels, test on both light and dark backgrounds

### 4. **Stale closures in useEffect dependency arrays cause silent failures**
- The click-outside-to-close handler's useEffect was missing 4 dropdown state variables from its dependency array
- The handler captured stale `false` values, so click-outside never fired for those dropdowns
- This was a pre-existing bug masked by the fact that the More panel partially contained these dropdowns — users rarely clicked outside them
- Rule: when adding new state variables that are read inside a useEffect, always add them to the dependency array

### 5. **`checkIfBlankImage` was orphaned code**
- The function existed and was called from nowhere in the grid/list views — only from an old code path
- The cover grid showed broken image icons for failed loads because no `onError`/`onLoad` was wired up
- Discovered during dark mode testing when trying to verify the placeholder appearance
- Rule: when writing detection/utility functions, wire them up at the call sites immediately, not "later"

## 🤖 AI Collaboration Insights

### Practices That Required User Prompting
- **UX hat for dropdown behavior**: User asked "is this intentional?" about checkbox dropdowns lacking hover — AI had flagged it as a technical bug but hadn't evaluated the UX design question
- **Identifying same-color variables**: User tested and reported invisible hover. AI should have caught that `--bg-hover` and `--bg-elevated` were identical during palette design
- **Broken cover discovery**: User tried to test the placeholder for dark mode, found that no covers in their library triggered it, and discovered a real broken cover that the detection missed. AI had converted the color to a variable without verifying the feature actually worked

### What Ground Rules Helped
- **Stop and ask**: The phased plan with user approval prevented overcommitting to the wrong approach
- **Commit before test**: 20 alpha commits meant every issue could be isolated to a specific change
- **UX expert role**: User asking for UX analysis on dropdown behavior led to discovering the stale closure bug and missing hover handlers — a broader fix than "just add dark: classes"

## 💡 Recommendations for Future

### 1. **Verify interactive state pairs during palette design**
- For every `--bg-X` and `--bg-X-hover` (or equivalent interactive pair), verify they produce a visible difference on the target background
- A simple checklist: "can a human see the difference between these two colors on this surface?"

### 2. **Add `onError`/`onLoad` to new image elements as standard practice**
- Any new `<img>` added to the codebase should include error handling from day one
- Pattern: `onError={() => fallbackHandler(id)}` + `onLoad={(e) => validateDimensions(e.target, id)}`

### 3. **HC themes as a separate version**
- The `[data-theme="hc-light"]` and `[data-theme="hc-dark"]` blocks are empty placeholders in CSS
- These can be filled in as a separate version when needed — the infrastructure supports N themes via `data-theme`

## Final Thoughts

The CSS ancestor-selector override approach was the key architectural win. The original design doc estimated 14-22 hours with per-element `dark:` class changes to ~1,275 className strings. The override approach delivered full dark mode in ~8-10 hours across 20 alphas with zero changes to JS className strings. The main cost was debugging edge cases (form elements, `!important` vs inline styles, same-color variables) that are inherent to any theming approach.

The biggest non-dark-mode wins were discovered during testing: the dropdown mutual exclusion fix, stale closure dependency array bug, and broken cover image handling. Dark mode testing is an effective smoke test for the entire UI because it forces you to look at every surface.

**Key Takeaway**: CSS-level theme overrides via ancestor selectors can deliver full dark mode without touching application code — but verify every interactive state pair produces visible contrast in both palettes.
