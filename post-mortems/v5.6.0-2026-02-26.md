## 🎯 What Worked Well

### 1. **Checklist-driven development (1A–1K)**
- The DESKTOP-BACKLOG.md checklist with labeled sub-items (1A through 1K) provided clear scope boundaries for each commit
- Each item was independently testable and committable — no "big bang" integration step needed
- The checklist survived multiple session boundaries and context compactions without losing state
- **Lesson**: For multi-faceted features, enumerate all sub-features upfront with letter codes. This creates natural commit boundaries and makes progress visible across sessions

### 2. **Unified position system for interleaved rendering**
- Tag views needed to appear among real folders in the left pane, each draggable to reorder independently
- Solution: folders get `displayPos = sortIndex * 2` (even numbers), tag views use float `position` values. Merged array sorted by position for rendering
- This avoided restructuring the existing folder data model while supporting arbitrary interleaving
- **Lesson**: When adding a new item type to an existing ordered list, a parallel position system with interleaving (even/float) is simpler than merging into a single position scheme

### 3. **Drag semantics designed before implementation**
- Defined all 4 drag combinations upfront (folder→tag, tag→tag, tag→folder, within-tag) with clear semantics: add-tag, move/copy, disallow, reorder
- Each had a distinct undo action type with appropriate reversal logic
- No ambiguity during implementation about what each drag should do
- **Lesson**: For drag-and-drop features, enumerate every source→destination combination and define semantics before coding. The matrix is small but the edge cases compound

### 4. **Tag Manager modal redesign emerged organically**
- Started as a simple pin toggle (1C) but user feedback during testing revealed the modal needed a full UX pass
- Went through 8 alpha iterations (alpha.13–alpha.20) — single sortable table, icon-based actions, full-bleed headers, orphaned section
- The final design was significantly better than what a pre-planned spec would have produced
- **Lesson**: Some UI components need iterative refinement during testing, not upfront specification. Budget for it

### 5. **Phase 8B (mobile tag views) was trivial because desktop was well-architected**
- Mobile needed: read `pinnedTagFolders` from backup, render in drawer, render as dashboard shelves, handle tag view IDs in FolderView
- Total: 1 commit, ~100 lines of code, completed in under an hour
- This was only possible because desktop exported clean data (`pinnedTagFolders` with `bookOrder`) and the tag view ID pattern (`__tag_{tagId}__`) was consistent
- **Lesson**: When building a feature that will be consumed read-only by another platform, invest in clean data export. The mobile implementation becomes almost free

### 6. **User wordsmith feedback on README/index.html**
- User provided ~12 specific feedback items with professional tech writer perspective
- Caught real problems: "control plane" jargon, unnecessary "desktop" labels, missing mobile mentions, stale column references
- The review-then-apply pattern (evaluate each item, push back where warranted, apply agreed items) produced better copy than either party alone
- **Lesson**: Treat documentation updates as a collaborative review, not a unilateral rewrite

## ❌ Mistakes Made

### 1. **Emoji icons don't respond to CSS color — discovered twice**
- First hit in alpha.10: pin/unpin toggle used 📌/📍 emojis, but `text-gray-400` had no visible effect
- Fixed by switching to inline SVG components (`TagIconSVG`, `FolderIconSVG`) that accept `className` for color
- This was the same lesson from the dark mode post-mortem (✨ sparkles replacing 🪄 wand) — not retained
- **Fix**: Memory updated. Rule: never use emoji for UI elements that need color changes. Use SVG

### 2. **React hook violation in conditional orphan tags section**
- Alpha.14 fix: the orphaned tags section was conditionally rendered with hooks inside the conditional block
- Manifested as: "React has detected a change in the order of Hooks"
- **Fix**: Moved hooks above the conditional. Standard React rule, but easy to violate when building conditional UI sections iteratively

### 3. **Android PWA icon cache aggressiveness**
- After pushing updated maskable icons to dev, user couldn't see changes on Android despite confirmed GitHub deployment
- Removing the home screen shortcut does NOT clear the manifest/icon cache
- Required clearing Chrome site storage (Settings → Site Settings → Storage → Clear & Reset)
- Cost 2 extra alpha cycles (icon padding iterations) partly because cache made it hard to verify changes
- **Fix**: Documented the cache clearing procedure. When testing PWA manifest changes on Android, always clear site storage first

### 4. **First maskable icon attempt had insufficient padding**
- The ReaderWrangler logo's lasso extends far, requiring more than the minimum 10% safe zone padding
- First padded version (alpha commit `15b20d1`) still clipped the lasso top in the Android adaptive icon circle
- Second version with more aggressive padding worked
- **Fix**: For logos with extended elements (ropes, antennas, tails), test at 15-20% padding, not just the spec minimum 10%

### 5. **README.md and index.html drifted out of sync**
- README still had 8 "column" references from the v4 era while index.html had been updated to v5 "folder" language
- The "Then browse your curated library on your phone" sentence was added to README but missing from index.html's matching paragraph
- **Fix**: Synced both files in the wordsmith pass. Going forward, the release checklist explicitly calls out "README.md (and its mirror index.html)" — but this drift happened over multiple releases without being caught

## 📚 Lessons Learned

### 1. **`bookOrder` was a late addition that should have been in the original data model**
- `pinnedTagFolders` was initially `[{tagId, position}]` (1A)
- Manual ordering within tag views (1G) required adding `bookOrder: [asin1, asin2, ...]` to each entry
- If `bookOrder` had been in the 1A data model, the 1G implementation would have been simpler
- Takeaway: when designing a "view" that displays books, always include an ordering field from day one — views without ordering are just filters

### 2. **Warm/cool tints are subtle but effective for cognitive wayfinding**
- Folder views get warm canary (`#fffef5`), tag views get cool blue (`#eef2ff`)
- Users can tell "where they are" without reading the breadcrumb — the color temperature signals the view type
- Both tints have dark mode variants and are defined as CSS classes (`.folder-view-tint`, `.tag-view-tint`)
- Applied to both desktop and mobile

### 3. **PWA manifest `purpose: "any maskable"` is a pragmatic compromise**
- Spec recommends separate icons for `any` and `maskable` purposes
- Using `"any maskable"` on a single icon with adequate padding works for 99% of cases and avoids maintaining duplicate icon sets
- The key constraint: logo must fit within the inner 80% circle (the maskable safe zone)

### 4. **Apple PWA meta tags are fire-and-forget**
- `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title` are standard, well-documented, and don't require iOS testing to implement correctly
- The iOS hint banner (localStorage-dismissed, iOS-only detection via userAgent) is similarly standard
- Acceptable to ship without device testing for standard patterns like these

## 💡 Recommendations for Future

### 1. **Include ordering fields in data models from day one**
- Any "view" or "collection" that displays books should have a `bookOrder` array from the initial schema
- Retrofitting ordering is more work than including it upfront (even if initially unused)

### 2. **Test PWA changes with cache clearing as standard procedure**
- Android caches manifest and icons aggressively
- After pushing PWA manifest/icon changes, always clear Chrome site storage before testing
- Consider adding a cache-busting query parameter to icon URLs in manifest.json if this becomes a recurring issue

### 3. **Keep README.md and index.html in sync per release checklist**
- The release checklist already says "README.md (and its mirror index.html)" but this drift happened over multiple releases
- Consider a future lint script that compares key sections (The solution, Key Features, How It Works, Recent Features) between the two files

## Final Thoughts

v5.6.0 was a "capstone" release that shipped the last two major features before public launch: tag virtual folders on desktop (11 sub-features) and the mobile viewer's final phases (tag views, PWA polish, documentation sync). The checklist-driven approach (1A–1K) was the key organizational win — it kept a complex feature tractable across multiple sessions and context compactions.

The most satisfying result was Phase 8B: mobile tag views required just 1 commit and ~100 lines because the desktop architecture was clean. This validates the principle of investing in data model design — when the export format is right, the consumer is almost free.

The README/index.html wordsmith pass was a reminder that documentation is a product surface too. The user's tech writer perspective caught issues that no amount of AI rewriting would have found — jargon creep, unnecessary labels, sync drift between files.

**Key Takeaway**: For features that span desktop and mobile, invest in the data model and export format. The mobile implementation becomes almost trivial when the desktop does the hard work of organizing clean, well-structured data.
