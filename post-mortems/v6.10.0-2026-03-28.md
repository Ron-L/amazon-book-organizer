## 🎯 What Worked Well

### 1. **Saved Filter Views — Independent Lens Design**
- Started as "pin tag to sidebar" replacement. User identified critical UX flaw: applying view filters would overwrite active filters.
- User proposed the "independent lens" model: stash filters on enter, apply view filters, gray out filter bar, restore on exit. Purple banner distinguishes views from user-set filters.
- Result is genuinely better UX than the original design — came from stopping to think about real usage patterns.
- **Lesson**: UX evaluation before implementation (as CLAUDE.md prescribes) caught a problem that would have required a rewrite.

### 2. **Two-Level Data Freshness — Research Before Build**
- Before designing the polling feature, thoroughly researched why the old manifest system failed (v3.8.0 post-mortem: browser domain isolation killed both file polling and IndexedDB approaches).
- Confirmed the relay eliminates both historical blockers. Also verified Cloudflare free tier quotas support polling (~350 users at 10-min intervals).
- Built on existing infrastructure: `checkStatus()` endpoint already existed, manifest already contains timestamp.
- **Lesson**: 30 minutes of research prevented repeating a mistake that cost significant time in v3.6-3.8.

### 3. **Video Script Updates — Batched Efficiently**
- Updated 4 video scripts (Videos 1, 4, 5, 8) in one pass to incorporate new features (saved views, Tag from Collections, Share Book, data freshness).
- Demo library decision (use 118-book whitelist, not personal library) caught before any recording happened.
- One-way data flow messaging (Amazon → App only) was user-prompted and critical for user trust.
- **Lesson**: Updating scripts alongside feature work ensures documentation doesn't drift.

## ❌ Mistakes Made

### 1. **View Folder Validation — Missed in Initial Implementation**
- `selectedFolderId` validation useEffect didn't recognize `__view_*__` IDs. Views immediately reset to All Books on the next render cycle.
- Root cause: `VIRTUAL_IDS` set was hardcoded and view folder IDs weren't in the `folders` array, so they failed the existence check.
- Took a separate alpha (alpha.27) to diagnose and fix what should have been caught during the initial view implementation.
- **Fix**: Added `if (isViewFolder(selectedFolderId)) return;` guard before the existence check. Should add view patterns to the validation logic earlier in future features.

### 2. **Tag Manager Drag-to-View — 6 Alphas of Iteration**
- Alpha.19 through alpha.24 were consumed by modal hide/show issues during drag operations (React re-renders, CSS vs unmount, backdrop visibility, inline rename conflicts).
- Each fix uncovered the next issue. Should have prototyped the drag-from-modal interaction more carefully before committing to the approach.
- **Fix**: Final solution (direct DOM style manipulation to hide modal during drag, restore on dragEnd) is solid but was expensive to reach.

### 3. **Debug Console.log Accumulated**
- 20+ debug console.log statements accumulated across the view, relay, and tag features. Nearly pushed to prod with them.
- Caught during release prep but should have been cleaned incrementally.
- **Fix**: Cleaned in a dedicated commit. Consider a pre-push check for debug logging patterns.

## 📚 Lessons Learned

### 1. **Relay Unlocks Features That Were Impossible Before**
- The file-based architecture (pre-v6.0) made cross-domain coordination impossible due to browser security. The relay is a neutral intermediary that both the fetcher and app can access.
- Data freshness polling, which was attempted and abandoned twice (v3.6.0 file polling, v3.6.1 IndexedDB manifest), is now trivially implementable: one `GET /status/{channelId}` call returning a JSON manifest.
- The relay's plaintext manifest (timestamp, bookCount) is the perfect lightweight signal — no decryption needed for freshness checks.

### 2. **Option B Dismiss Pattern — Respectful Notifications**
- When polling surfaces a "new data available" banner, dismissing it records the specific timestamp. The banner only reappears when a genuinely new fetch produces a different timestamp.
- This avoids the nag problem (Option A: re-show every 10 min) and the amnesia problem (Option C: forget entirely until page reload).
- Simple implementation: one ref (`dismissedRelayTimestampRef`) checked during poll.

### 3. **Demo Library Privacy Decision**
- User caught that video scripts assumed showing his real 2,500-book Amazon library. The whitelist fetcher limits to 118 demo books, but Amazon's "Your Books" page briefly shows real covers.
- Solution: limit Amazon page exposure to a couple of rows, remove specific book counts from overlays, use generic language ("Got a Kindle library?" instead of "Have 2,500 books?").
- **Lesson**: Privacy considerations for screen recordings should be part of video planning, not discovered during production.

## 🤖 AI Collaboration Insights

### Practices That Required User Prompting
- **UX lens model**: Claude's initial design applied view filters directly, overwriting user filters. User identified the real-world usage pattern (look at a view, then return to my filters) and proposed the stash/restore approach.
- **One-way data flow messaging**: User emphasized that video narration must be explicit about Amazon → App only. "All this work on his tags is NOT going to be reflected back in Amazon or in his Kindle."
- **Demo library privacy**: User caught the "2,500 books" assumption in scripts. Claude had written those scripts without considering that the recording would show real data.
- **Debug cleanup**: User had to prompt removal of console.log output before prod push.

### What Ground Rules Helped
- "Discussion ≠ approval to act" — the freshness design discussion was extensive before any code was written.
- "UX analysis before implementing" — the lens model emerged from a UX discussion, not from coding first.
- "STOP and ASK" — prevented premature implementation multiple times during the video script updates.

## Final Thoughts

This release bundled four user-facing features (saved views, share book, tag from collections, data freshness) plus significant video production planning. The standout was the lens model for saved views — what started as a simple "apply filters" implementation became a thoughtful stash/restore UX that respects the user's active filter state. The data freshness feature was satisfying because it finally delivered something that was attempted and abandoned twice before, made possible by the relay infrastructure from v6.0.

**Key Takeaway**: The best features in this release came from UX discussion before code — the lens model and the two-level freshness design both emerged from stopping to think about real usage patterns rather than jumping to implementation.
