## ✅ What Worked Well

### 1. **Telemetry-to-fix loop closed without a user bug report**
This is the first release shipped purely on the strength of the `newOwnershipType=*` signal. The v4.10.0 design decision — "instrument unknowns rather than speculate" — paid for itself five months later. No user had to file an issue, screenshot a missing badge, or describe a confusing dropdown. The signal arrived, was actionable, and led to a same-session patch.

### 2. **Stop-and-ask discipline held**
Even though the change was small, presented exact label/badge choices ("Amazon Insider" / purple "INSIDER" badge) and version bumps before editing. User approved the choices in one round, including a screenshot demonstrating "INSIDER" fits the badge slot fine in proportional font. No re-edits needed.

### 3. **Single alpha → release**
Unlike 6.11.2's 12-alpha grind, this was minimal-surface-area work: add an enum value at every site that enumerates it. One alpha, user-verified the dropdown and filter visually (couldn't test badge — no books of that type), released.

## ❌ Mistakes Made

### 1. **Two Edit-before-Read failures during release commit**
Tried to Edit `readerwrangler.html` and `index.html` in the same parallel batch as files I'd already Read. Both Edits rejected because the harness tracks per-file Read state. Cost: one extra Read pair + retry. Trivial in time, but a tell that I batched without checking which files I'd actually opened.
- **Lesson**: When editing in parallel across many files, verify the Read set first. The harness rule is per-file, not per-session.

### 2. **Speculation framing could have been tighter**
When the user asked what `InsideAmazon` means, I gave three speculative guesses (employee program / First Reads / Publishing imprints). User's Google search produced the most informative answer (employee internal testing). I had access to WebSearch but reached for speculation first.
- **Lesson**: For "what does this Amazon string mean?" questions, a WebSearch is cheaper than three guesses.

The minimal-patch choice was correct for this scope, but if a 6th ownership type shows up via telemetry, the right move is to extract a single `OWNERSHIP_TYPE_LABELS` constant + a `formatOwnershipLabel()` helper consumed by the active-filters bar, dropdown header, and filter-status-bar.

**Threshold to revisit**: next unknown ownership type. If one arrives, refactor first, then add the type — turns the 9-touch-point patch into a 2-touch-point one (constant + switch case).

## 🔗 Follow-Up Items

1. **`integrity-homeless` event** — same user fired this alongside `newOwnershipType`. Per [DATA-INTEGRITY.md](../docs/design/archive/DATA-INTEGRITY.md), homeless books on a fresh import shouldn't happen. Three candidate causes: (a) import bug writing to IndexedDB without updating Inbox bookIds, (b) race between integrity check and import completion, (c) user action between fetch and import. Worth a separate investigation session.

2. **Amazon Insider observation as a launch-strategy signal** — if `InsideAmazon` really is an employee/internal-testing program, an Amazon employee may have installed ReaderWrangler. Doesn't change anything operationally, but reinforces the existing low-key launch plan ([COMMUNITY-SHARING-PLAN.md](../.private/COMMUNITY-SHARING-PLAN.md)) — keep below corporate-radar height, skip the LinkedIn announcement for now.
