## 🎯 What Happened

Ron asked for a systematic tooltip inventory while at dinner. Dispatched a general-purpose agent to walk readerwrangler.js + mobile.js — ~155 elements scanned, returned a categorized list of HIGH/MEDIUM/LOW gaps with proposed text. Ron approved the full HIGH+MEDIUM list. Implemented in alpha.1 (19 additions). Ron tested on phone via `ron-l.github.io/readerwranglerdev/...` — and reported "long-press does nothing" on the mobile tooltips.

That triggered the correction: native HTML `title` attribute doesn't render as a visible tooltip on touch devices in modern Chrome (long-press is reserved for context menus and selection). The mobile additions had zero visible effect for actual touch users. Course-correct in alpha.2: keep `title` (still useful for desktop-mode + some accessibility) and add `aria-label` (the right accessibility primitive for icon-only controls — screen readers announce it).

Released as 6.11.9.

Walking 155 interactive elements across two files (~17k + ~2.6k lines) is exactly the kind of work that swamps the main loop's context budget but fits a focused sub-agent perfectly. The agent returned a categorized, scannable report with proposed text per item. Cost: one Agent invocation while Ron was at dinner; benefit: hours of grep+read+propose distilled into a 1500-word report. Same pattern as the morning's PM synthesis. Two-for-two on "high-volume systematic walks belong in sub-agents."

### 2. **Caught two false positives in the agent's report before editing**
The agent flagged "column headers lack sort tooltips" and "Data Status indicator lacks tooltip." Reading the actual code (lines 13064 and 6328) showed both already had tooltips. Caught both with a targeted verification read before any Edit. The lesson is in [[feedback_rules_vs_mistakes]] — verify against source, not against intermediate reports. Sub-agent output is intermediate.

### 3. **The release-itself stayed disciplined**
Two alphas, both with single-line spot-check instructions. Standard release flow. APP_VERSION + ORGANIZER_VERSION + softwareVersion + CHANGELOG + push prod + push dev — same script as the other v6.11.x releases. No deviations.

## ❌ Mistakes Made

### 1. **Should have caught "title doesn't render on touch in modern Chrome" before Ron tested**
This is the headline mistake. The fact that mobile Chrome stopped rendering `title` tooltips on long-press around v85 is well-known platform behavior — not an obscure quirk. The agent's inventory note ("tooltips on touch devices only appear on long-press in many browsers") was already a hedge that should have prompted me to verify. I forwarded the agent's claim into the implementation without confirming it.

The cost was real: Ron added the alpha to dev, pushed it to `ron-l.github.io/readerwranglerdev/`, loaded it on his phone, long-pressed every icon expecting tooltips, got nothing. Round-trip wasted. Worse, the failure mode pattern-matches "Claude assured me X works, X doesn't work" — exactly the trust signal we don't want.
- **Lesson — memory candidate:** before recommending any UI primitive for *touch devices*, verify the primitive's behavior on touch. `title` on touch is a known regression; `tabindex` behaves differently; `:hover` styles don't translate; focus events are tricky. Worth a memory entry. Touch ≠ desktop, even when the markup is the same.

### 2. **Mis-counted "7 mobile elements" when there were actually 9 instances**
Said "7 mobile elements" in my approval-request message; actually added 9 title attributes (back-arrow + close icons each appeared twice, plus search-bar clear). Minor — didn't affect outcome — but a precision miss. When proposing a numbered change, count from the actual code, not from a mental model.

### 3. **The agent's "outdated" note was a quiet flag I missed**
In the inventory report the agent wrote: *"tooltips on touch devices only appear on long-press in many browsers, so the value is real but lower than desktop."* That's a hedge. A careful reader would have followed up with "what does 'many browsers' mean in 2026?" I didn't. Wrote off the hedge as an aside instead of treating it as the open question it was.
- **Lesson — for future delegated audits:** treat sub-agent hedges ("usually," "in many browsers," "typically") as TODO items. They flag where the agent itself wasn't sure. Either verify before acting or surface the uncertainty to Ron for a decision.

## 🏗️ Technical Debt Flagged

**The agent flagged Tag from Collections wizard as worth a separate audit pass.** Filed as TODO 7e (LOW/LOW, ~1 hour). The wizard is a critical workflow (converting Kindle Collections → editable tags) — discoverability of its controls is launch-relevant. Not blocking.

**Mobile sort cycle button was intentionally not given `aria-label` in alpha.2** because it has visible text (`"Sort: Date Added"` etc.) that screen readers announce. Adding `aria-label` would *override* the visible label and lose the state info. This is the right call but it relies on a subtle aria-label-vs-text-content rule that future-me should remember. Worth noting in case of any future "should this also get aria-label?" question.
