## What Happened

### The Problem

**Old dialog (EULA-like text):**
```
✅ Backup Restored!
📥 Library file regenerated (2578 books)

⚠️ IMPORTANT: Replace your existing amazon-library.json file

When the save dialog appears:
   • Navigate to where you keep amazon-library.json
   • If browser suggests "amazon-library (1).json",
     change it back to "amazon-library.json"
   • Save to replace the existing file

💡 Why this matters:

This regenerated file contains ALL your books (owned + wishlist).
Using it for future Library Fetcher runs ensures ALL your books get updated,
preventing stale data for wishlist items.
```

**User feedback:** "I feel it looks a bit like EULA text people will ignore."

**Danger:** Users might:
- Save as `amazon-library(1).json` instead of replacing
- Skip the download entirely (click OK without saving)
- Not understand why replacement matters

**Consequences of skipping:**
- Next bookmarklet fetch uses OLD amazon-library.json
- Imports wrong book set (different account or time period)
- Organization intact BUT contaminated with wrong books

### Root Cause

**Design issues:**
1. **Wall of text** - Paragraph format hard to scan
2. **Buried action** - Critical instruction hidden in bullets
3. **Passive tone** - "When the save dialog appears" (not action-oriented)
4. **Mixed messages** - Explains "why" before "what"
5. **Incorrect help text** - Claimed organization would disappear (wrong - it's stored separately)

### The Fix

**Created custom post-restore dialog (`showBackupRestoredDialog`):**

**Visual design:**
```
┌─────────────────────────────────────────────────┐
│ ✓ Backup Restored (2578 books)                 │
│                                                  │
│ Next: Update your library file                   │
│                                                  │
│ When the save dialog appears:                    │
│ ✓ Keep filename: amazon-library.json            │
│ ✓ Replace existing file                         │
│ ✗ Don't save as amazon-library(1).json          │
│                                                  │
│ 💡 This keeps your bookmarklet in sync          │
│                                                  │
│ [?] Why replace?    [Save File]    [Cancel]     │
└─────────────────────────────────────────────────┘
```

**Implementation details:**

1. **New function** (lines 112-211): `showBackupRestoredDialog(bookCount)`
   - Returns Promise<boolean> (true = Save, false = Cancel)
   - Custom styled modal with action buttons
   - Green title (success color)
   - Checklist format with ✓/✗ symbols

2. **Three buttons:**
   - **"? Why replace?"** - Opens help popup explaining workflow
   - **"Cancel"** - Closes without saving (resolve false)
   - **"Save File"** - Triggers download (resolve true)

3. **Help popup** explains:
   - Backup contains: Library data + Organization
   - When restored: Organization loaded, library needs updating
   - If skipped: Next fetch loads prior data, may mix accounts

4. **Conditional download** (lines 3350-3365):
   - Only triggers if `shouldSave === true`
   - Logs cancellation if user skips

## Lessons Learned

### 1. **Verify Design Details After Compaction**

**Problem:** Compaction summarized detailed UI mockup as "checklist format dialog" without preserving layout, button labels, or positioning (before vs after restore).

**Pattern:** When compaction happens mid-design discussion:
- ❌ Don't implement from summary alone
- ✅ Ask user: "Can you share the pre-compaction design details?"
- ✅ Or search transcript file if available

**Prevention:**
```markdown
## Before implementing post-compaction:
- [ ] Ask: "Did compaction lose critical design details?"
- [ ] Review: Original user request vs summary
- [ ] Verify: UI mockups, button labels, dialog flow
- [ ] Confirm: When/where dialog appears in workflow
```

### 2. **Understand Data Architecture Before Writing Help Text**

**Problem:** Help text claimed "your organization will disappear" because I didn't understand:
- Organization stored separately from book data (different localStorage keys)
- Skipping regeneration only affects NEXT fetch (not current state)
- Danger is account contamination, not data loss

**Better approach:**
1. Read storage code first (localStorage keys, IndexedDB structure)
2. Trace restore workflow (what gets loaded where)
3. Identify actual danger (wrong books imported on next fetch)
4. Write help text based on code, not assumptions

**Checklist:**
```markdown
## Before writing user-facing explanations:
- [ ] Read relevant code sections
- [ ] Trace data flow through system
- [ ] Identify actual vs perceived dangers
- [ ] Verify claims against implementation
```

### 3. **Mermaid Diagrams Require VS Code Extension**

**Discovery:** User couldn't see Mermaid diagrams in VS Code preview without extension.

**Solution:** Recommend "Markdown Preview Mermaid Support" by Matt Bierner

**Note:** GitHub renders Mermaid natively, so diagrams work in repo even if not local.

**Documentation pattern:**
- Create Mermaid in markdown (GitHub-compatible)
- Include installation note in docs if needed
- Split complex diagrams into separate blocks (avoid horizontal layout)

### 4. **Action-Oriented Dialog Design**

**Old pattern (informational):**
```
Title: Information Message
Body: Long explanation of what happened
Button: OK
```

**New pattern (action-oriented):**
```
Title: What Happened (status)
Body: What You Need To Do (imperative)
      ✓ Do this
      ✗ Don't do that
Buttons: [Help] [Action] [Cancel]
```

**Benefits:**
- User knows what to do immediately
- Checkmarks provide visual scanning cues
- Help available but not required
- Action button explicit (not just "OK")

### 5. **CONTRIBUTING.md "Understanding the Codebase" Section**

**Best practice:** Link to technical docs from CONTRIBUTING.md without bloating it.

**Structure:**
```markdown
## Understanding the Codebase

### Core Documentation
- [Architecture] - System design
- [Data Flow] - Backup/restore workflow
- [Schema] - Data structures

### Key Patterns
- Brief summary of each pattern
```

**Benefits:**
- New contributors find architecture docs easily
- CONTRIBUTING.md stays focused on process
- Technical details live in appropriate locations

## Technical Details

### New Dialog Function

**Location:** readerwrangler.js lines 112-211

**Signature:**
```javascript
function showBackupRestoredDialog(bookCount)
```

**Returns:** `Promise<boolean>`
- `true` - User clicked "Save File"
- `false` - User clicked "Cancel"

**Usage:**
```javascript
const shouldSave = await showBackupRestoredDialog(mergedBooks.length);
if (shouldSave) {
    // Trigger download
} else {
    console.log('⚠️ User cancelled library file download');
}
```

### Storage Architecture

**Organization stored separately from books:**

**localStorage keys:**
- `readerwrangler-folders` - Folder structure (explorerFolders)
- `readwrangler-explorer` - View settings (explorerSort, explorerView)
- Custom sort order embedded in folder bookIds array

**IndexedDB:**
- `ReaderWranglerDB.books` - Book objects with user metadata

**This separation means:**
- Restoring backup updates BOTH storage locations
- Skipping amazon-library.json regeneration only affects future fetches
- Organization survives even if library file is stale
- Danger is contamination (wrong books), not loss (organization gone)

### Mermaid Diagram Structure

**Three separate diagrams** (stacked vertically):

1. **Normal Flow:** Fetch → Library File → App → Backup
2. **Restore Flow:** Backup → App → Regenerate Library (CRITICAL)
3. **Danger Scenario:** Skip regeneration → Account contamination

**Color coding:**
- Blue (#e7f3ff): User files (backup, amazon-library.json)

## Backup/Restore Workflow (Final Design)

### User Flow

1. **File → Import Backup**
2. Select backup.json file
3. Confirm initial prompt: "Restore backup?"
4. **App restores data** (books → IndexedDB, organization → localStorage)
5. **NEW DIALOG APPEARS:** "✓ Backup Restored (X books)"
6. User reads instructions with checkmarks
7. User clicks "? Why replace?" to see help (optional)
8. User clicks "Save File" → Browser shows save dialog
9. User navigates to existing amazon-library.json location
10. User replaces file (same name, same location)
11. **Done** - Organization and library file now in sync

### Danger Scenario Prevented

**Without regeneration:**
```
Backup (Account A) → App (Account A books + org)
                  → amazon-library.json still has Account B books
                  → Next fetch imports Account B → CONTAMINATION
```

**With regeneration:**
```
Backup (Account A) → App (Account A books + org)
                  → amazon-library.json updated to Account A
                  → Next fetch imports Account A → CORRECT
```

**Dialog prevents this by:**
- Making regeneration a clear action ("Save File" button)
- Explaining danger in help popup
- Providing cancel option if user wants to skip
