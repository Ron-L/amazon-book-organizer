## What Happened

### The Problem

After v5.0.4 restored wishlist filtering to Source dropdown, the old `wishlistFilter` state variable remained in code but was completely unused:
- No UI to set it (removed in v5.0.0)
- Always empty string (never changed by user)
- Still referenced in 23 locations (filter logic, localStorage, status banner, etc.)

**User's insight:** Dead code creates cognitive overhead for future code readers who might spend time trying to understand its purpose or relationship to the new Wishlist option in Source dropdown.

### Root Cause

**v5.0.0 removed the wishlist filter UI but not the underlying code.**

In v4, there were TWO separate filters:
1. Wishlist filter (❤️): All Books | Owned Only | Wishlist Only
2. Ownership Type filter (🏷️): All Types | Purchased | Sample | etc.

v5.0.0 consolidated these into a single Source dropdown but only removed the UI, leaving:
- `wishlistFilter` state variable ✗ (unused)
- `setWishlistFilter` setter ✗ (never called)
- Filter logic checking `wishlistFilter` ✗ (always true due to empty string)
- localStorage save/restore ✗ (always empty string)
- Status banner display ✗ (never shown)

### The Fix

**Systematic removal of all 23 references:**

## Lessons Learned

### 1. **Remove Dead Code Immediately**

When removing a feature:
1. Remove UI
2. Remove state variables
3. Remove all references
4. Remove from localStorage schema

Don't leave unused code "because it's not hurting anything" - it creates confusion.

### 2. **Dead Code Audit Checklist for Major Refactorings**

After major UI redesigns (like v5.0.0), explicitly check:
- [ ] Are all v4 state variables still used?
- [ ] Are all localStorage keys still used?
- [ ] Are all filter variables still connected to UI?
- [ ] Are all status banner fields still active?

Search for: `useState`, `localStorage.getItem`, `setX(` to find unused setters.

### 3. **Runtime Code Changes = Version Bump**

User's correction was crucial:

> "There are user facing changes. The code is different. We HOPE it acts exactly as before but can never be sure. If a user reports a bug and give us the App version 5.0.4, which is it?"

**Rule:** Only skip version bump for:
- Documentation changes (README, CHANGELOG, TODO)
- Comments
- Code formatting (whitespace, indentation)

Everything else that affects runtime = version bump.

### 4. **Grep is Your Friend for Code Cleanup**

Systematic approach:
```bash
# Find all references
grep -n "variableName" file.js

# Remove one by one, verify after each edit
# Re-grep to confirm all gone
grep -n "variableName" file.js  # Should return nothing
```

### 5. **Code Readers > Code Writers**

User's insight: "Code reader may spend time chasing deadends"

Code is read 10x more than it's written. Dead code creates:
- Confusion about purpose
- Wasted time tracing logic
- False assumptions about relationships
- Maintenance burden (updating comments, etc.)

Better to remove it.

## Technical Details

**Removed State Variable:**
```javascript
// BEFORE:
const [wishlistFilter, setWishlistFilter] = useState(''); // '' | 'owned' | 'wishlist'

// AFTER:
// (removed entirely)
```

**Filter Logic Cleanup:**
```javascript
// BEFORE:
const matchesWishlist = !wishlistFilter ||
    (wishlistFilter === 'wishlist' && book.onWishlist) ||
    (wishlistFilter === 'owned' && !book.onWishlist);

return matchesSearch && ... && matchesWishlist && matchesOwnership && ...;

// AFTER:
// (matchesWishlist removed entirely, only matchesOwnership remains)
return matchesSearch && ... && matchesOwnership && ...;
```

**Status Banner Cleanup:**
```javascript
// BEFORE:
{wishlistFilter && <span>Wishlist: {wishlistFilter === 'owned' ? 'Owned Only' : 'Wishlist Only'}</span>}

// AFTER:
// (removed entirely - never displayed because wishlistFilter always empty string)
```

**Why It Was Safe:**
The state variable was initialized to `''` (empty string) and never changed because:
1. No UI to set it (removed in v5.0.0)
2. No programmatic setter calls
3. localStorage always had `wishlistFilter: ''` from previous sessions

Therefore all filter checks like `!wishlistFilter` always evaluated to `true`, making the logic a no-op. Removing it had zero behavioral impact.
