**Date**: 2026-02-13
**Duration**: ~30 minutes
**Versions Iterated**: 1 alpha version (v5.5.1-alpha.1)
**Release Components**:

## 🎯 What Worked Well

### 1. **Parallel agent exploration for audit**
- Launched two Explore agents simultaneously: one to catalog all existing tooltips (found 50), another to find all interactive elements missing tooltips (scanned ~218 clickable elements)
- This produced a comprehensive cross-referenced audit in ~60 seconds that would have taken 20+ minutes of manual grep/read cycles
- **Lesson**: For audits that need both "what exists" and "what's missing", parallel agents with complementary search strategies are highly effective

### 2. **Priority-based triage**
- Categorized gaps into HIGH (icon-only controls, filter buttons), MEDIUM (modal close buttons), and LOW (text-labeled controls that are self-evident)
- The LOW category was explicitly excluded — context menu items, filter dropdown items, and bulk edit buttons don't need tooltips because their text labels are the affordance
- User chose "all of them" (HIGH + MEDIUM), which kept scope controlled while still being comprehensive
- **Lesson**: Presenting an audit with clear priority tiers lets the user make an informed scope decision

### 3. **User caught a compliance issue**
- AI recommended changing the Amazon affiliate tooltip ("Opens Amazon with affiliate link" → "View on Amazon") as a UX improvement
- User correctly identified it serves an Amazon affiliate disclosure requirement and should stay
- **Lesson**: Always ask before removing text that might serve legal/compliance purposes — what looks like bad UX might be a requirement

## ❌ Mistakes Made

### 1. **Recommended removing a compliance tooltip**
- Suggested changing the Amazon affiliate link tooltip without considering that affiliate disclosure is a legal requirement
- User caught this immediately: "it is there to satisfy Amazon disclosure requirements"
- **Fix**: Retracted the recommendation. For future audits, flag any tooltip containing "affiliate", "disclosure", or similar legal terms as requiring user confirmation before modifying

## 📚 Lessons Learned

### 1. **Tooltip tiers in this codebase**
- The audit established clear categories for when tooltips are needed:
  - **Always**: Icon-only buttons (×, +, pencil, arrows), controls with non-obvious behavior (shift+click), disabled states explaining *why*
  - **Standard practice**: Modal close buttons (universally understood but helps accessibility)
  - **Not needed**: Text-labeled buttons ("Apply", "Cancel"), visible dropdown items, context menu items with emoji+text labels
- This taxonomy can guide future feature additions without re-auditing

### 2. **Dynamic tooltips are more helpful than static ones**
- Best tooltips in the app are state-aware: "Turn off grouping" vs "Group by Author", "Show additional filters" vs "Hide additional filters"
- Static tooltips like "Close" are fine for simple actions but dynamic ones that reflect current state teach the user what will happen next
- The More button tooltip (`morePanelOpen ? 'Hide additional filters' : 'Show additional filters'`) is a good pattern to follow for toggles

### 3. **Disambiguation matters for rating controls**
- Changed "Clear rating" to "Clear my rating" — a small tweak, but the book dialog shows both Amazon ratings and the user's personal rating. Without "my", a user might worry they're affecting the Amazon rating
- Pattern: When a control operates on one of multiple similar-looking values, the tooltip should specify which one

## 💡 Recommendations for Future

### 1. **Add tooltips as part of new feature definition**
- Every new button or interactive control should include tooltip text in the plan/spec
- This prevents tooltip gaps from accumulating and requiring periodic audits
- Template: "What tooltip should this control show?" as a checklist item in plan mode

### 2. **Consider ARIA labels alongside tooltips**
- `title=` attributes provide visual tooltips but are not ideal for screen readers
- For the accessibility task (P3-T6), consider adding `aria-label` attributes where `title` alone is insufficient
- Low priority since the app is personal-use, but worth noting for the public release path

## Final Thoughts

A clean audit-driven release. The parallel agent approach made the audit fast and comprehensive, and the priority triage prevented scope creep (the LOW tier was explicitly excluded). The most valuable moment was the user catching the affiliate compliance issue — a reminder that tooltips can serve purposes beyond UX that aren't visible in the code.

**Key Takeaway**: When auditing existing UI text, always check whether it serves legal or compliance purposes before recommending changes — what looks like poor UX might be a requirement.
