## 🎯 What Worked Well

### 1. **Diagnostic-driven root cause analysis**
- Built progressively deeper diagnostics (alpha.21 → alpha.22) to prove that sidebar drag lag was NOT caused by React re-renders — only 2 renders occurred during a 44-second drag session
- This redirected investigation from React optimization (wrong path) to browser DOM overhead (correct path), which led directly to the drag virtualization solution
- **Lesson**: When performance intuition says "it must be re-renders," measure first. The diagnostic saved hours of optimizing the wrong thing

### 2. **User-driven design for drag virtualization**
- User proposed the key insight: "why not just hide the ones not in the view window?" — turning full-tbody-hide into a sliding window that preserves visual context
- User also identified the need for buffer on both sides (reorder within right pane, not just drag to sidebar), and defined the parameterized sliding window (edge trigger, shift size, buffer)
- **Lesson**: Users who understand the problem domain often propose better solutions than the developer. Present the constraint, let the user shape the approach

### 3. **Layered performance strategy**
- Four independent optimizations stacked cleanly:
  1. **Render cap** (200 items) — protects React render time
  2. **Drag virtualization** (sliding window) — protects browser DOM during drag
  3. **CSS containment** — isolates left/right pane paint cycles
  4. **Auto-expand guard** — prevents cascading re-renders during drag
- Each solves a different bottleneck. No single one was sufficient; together they make 10K books workable
- **Lesson**: Performance at scale requires attacking multiple layers (React, DOM, CSS, event handling) — a single optimization rarely suffices

### 4. **CSS containment as a one-line fix**
- `contain: layout style paint` on both panes eliminated the sidebar trailing-highlight lag that persisted even after all other optimizations
- This was the final piece that made the user say "Fixed at last!" — 2 lines of CSS
- **Lesson**: CSS containment (`contain` property) is a powerful and underused tool. When two sibling containers have independent scroll/paint behavior, `contain: layout style paint` can eliminate cross-pane paint interference

## ❌ Mistakes Made

### 1. **pointer-events:none was the wrong optimization (alpha.14-17)**
- Applied `pointer-events: none` on `<tbody>` during drag to prevent hit-testing overhead
- This caused two bugs: (a) stuck clicks after drag-to-folder (detached source row's dragend doesn't bubble), (b) broke within-folder reorder (drop targets became unhittable)
- The optimization addressed hit-testing, but the real bottleneck was React re-renders (at 10K items). It solved the wrong problem while creating new ones
- **Fix**: Removed entirely in alpha.19. The correct optimization was the render cap (reduce what React renders) and drag virtualization (reduce what the browser paints)

### 2. **Focused too long on React re-renders before measuring**
- Spent several alphas (alpha.19-21) assuming sidebar drag lag was caused by React re-renders, investigating state changes in drag handlers
- The diagnostic in alpha.22 proved only 2 renders in 44 seconds — the lag was browser DOM overhead, not React
- **Fix**: Should have instrumented renders earlier. Future performance work should start with "how many renders are actually happening?" before optimizing render paths

### 3. **Explore agent gave incorrect analysis**
- Launched an Explore agent to find drag handlers causing re-renders. It incorrectly identified `setFolderDropHighlight` as a state setter causing re-renders
- In fact, `setFolderDropHighlight` is entirely ref-based (classList manipulation, no React state)
- **Fix**: Don't trust agent analysis of performance-critical code paths without verification. Read the actual code

## 📚 Lessons Learned

### 1. **Detached DOM elements don't bubble events**
- When a `<tr>` is unmounted by React (book moved to different folder via `setFolders()`), the element becomes detached from the DOM. Its `dragend` event does NOT bubble to `window.addEventListener('dragend', ...)` — all three cleanup layers (onDragEnd, global dragend, useEffect) failed silently
- Fix: Add cleanup (`setExplorerDragBookId(null)`) to all 5 folder `onDrop` handlers, which run BEFORE React unmounts the source row
- **This is a fundamental HTML5 DnD trap**: any drag that causes the source element to unmount must handle cleanup in the drop handler, not the dragEnd handler

### 2. **Browser DOM overhead is real at 10K elements**
- With 10K `<tr>` elements, even pure CSS operations (highlight changes on sidebar) cause perceptible lag because the browser's compositor must account for all visible elements during paint
- `display: none` effectively removes elements from the paint tree — the drag virtualization hides ~9,700 of 10K rows, reducing paint work by ~97%
- The sliding window (100-row buffer, shift 50 at edge trigger of 20) keeps the visible area responsive while allowing scroll during drag

### 3. **CSS `contain` property for pane isolation**
- `contain: layout style paint` tells the browser: changes inside this element cannot affect siblings
- Without it, a classList change on a sidebar folder triggers a paint pass that includes all visible book rows in the right pane
- With it, each pane is painted independently — sidebar highlights become near-instant regardless of right pane content
- This single CSS property eliminated the "trailing focus" lag that persisted through all other optimizations

### 4. **Render cap is a UX pattern, not just a performance hack**
- Showing 200 items with "Show all N" is progressive disclosure: fast default, opt-in for the heavy view
- At 200 items: renders take 15-25ms (imperceptible). At 10K: 500-1000ms (blocking)
- The cap protects not just initial render but EVERY subsequent re-render (filter change, tag edit, selection)
- The user correctly identified this should stay even after drag virtualization — they solve different problems

## 💡 Recommendations for Future

### 1. **Measure before optimizing**
- Always instrument with diagnostics first (render count, timing) before applying performance fixes
- The alpha.22 diagnostic that proved only 2 renders in 44s saved the entire project from going down the wrong path

### 2. **CSS containment as standard practice**
- Consider adding `contain: layout style paint` to any independent scroll containers in future features (e.g., mobile viewer panes, dual-pane split)
- It's a zero-risk, zero-behavior-change optimization that prevents cross-container paint interference

### 3. **Drag virtualization could be generalized**
- The sliding window pattern (buffer + edge trigger + shift size) could be extracted into a reusable utility if future views need similar large-list drag support
- Current implementation is inline in the component; extracting to a helper would be a clean refactor

## Final Thoughts

This was the most diagnostic-heavy release in the project's history — 25 alphas across 2 context sessions, with a critical pivot when measurement proved the assumed bottleneck (React re-renders) was wrong. The real bottleneck (browser DOM overhead at 10K elements) required a fundamentally different solution: reduce what the browser sees during drag, and isolate pane paint cycles with CSS containment.

The most productive moments came from user-driven design: the sliding window concept, the buffer parameters, and the CSS containment suggestion all originated from collaborative discussion rather than AI-driven implementation. The 25 alphas included ~10 diagnostic/dead-end versions, but each narrowed the problem space until the right solution became clear.

**Key Takeaway**: At scale, performance bottlenecks migrate from your framework (React) to the browser itself (DOM, paint, compositing). The tools to fix them are different: not `useMemo` and `useRef`, but `display: none`, `contain`, and DOM-level virtualization.
