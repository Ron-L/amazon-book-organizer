## 🎯 What Worked Well

### 1. **Design Doc Before Implementation**
- A full design doc ([docs/design/DATA-INTEGRITY.md](../docs/design/DATA-INTEGRITY.md)) was written before any code, covering incident history, root causes, the integrity check system, UX decisions, and open questions
- User resolved all open questions in a single conversation turn, making implementation straightforward
- Writing the historical incident timeline revealed cross-cutting patterns (no write serialization, no operation locking, no invariant checking, no telemetry) that wouldn't have been obvious from the code alone
- **Lesson**: For systemic problems with multiple interacting causes, a design doc pays back immediately in clarity and avoids mid-implementation pivots

### 2. **Post-Mortem Research via Git + Code Archaeology**
- Used `git log --grep` plus reading code version comments to reconstruct a full incident timeline dating back to January 2026
- The CORRUPTED backup file (`readerwrangler-backup-2026-03-06 14.20-CORRUPTED.json`) confirmed the March 6 incident was real and had an artifact
- **Lesson**: The project has rich historical context in version comments, commit messages, and backup files — these are primary sources for post-incident analysis

### 3. **Pending-Flag Pattern for Post-Import Integrity Check**
- The problem: `loadLibrary` calls `setFolders` / `setBooks` asynchronously; by the time `importFromRelay` returns, React state hasn't committed the new values yet
- Solution: set `integrityCheckPending = true` in the finally block; a `useEffect` on `[integrityCheckPending, books, folders]` fires after React settles, with fresh state
- This eliminated all timing complexity without needing to thread books/folders through async call chains
- **Lesson**: When you need to act on "settled post-operation state" in React, a pending flag + useEffect is cleaner than trying to pass data explicitly through async call chains

### 4. **Swap Pattern for Hover Button/Count Overlap**
- Folder `+`/`×` buttons were hidden behind the book count because of absolute positioning
- Fix: `group-hover:hidden` on the count wrapper, `hidden group-hover:flex` on the buttons — they swap in place
- No layout shift, no z-index fighting, no absolute positioning needed
- **Lesson**: When two inline elements compete for the same visual space, a CSS swap (hide one, show other) on the same `group-hover:` trigger is cleaner than absolute positioning

### 5. **UX Analysis Before + Button Move**
- Before moving the `+` button, stopped to analyze where it semantically belonged
- Identified that All Books is a view (not a container) and the `+` had been placed there for accidental historical reasons
- My Library is the root container — creating a top-level folder = creating a child of My Library — exactly analogous to "Create Subfolder" on any folder
- **Lesson**: Button placement should follow semantic hierarchy, not implementation convenience

## ❌ Mistakes Made

### 1. **Wrong localStorage Key in Console Investigation Script**
- When diagnosing homeless books, initial console script used `'rw-folders'` instead of `'readerwrangler-folders'`
- Returned empty array, making every book appear homeless (hundreds of false positives)
- Had to grep `uiHelpers.js` for `FOLDERS_KEY` to find the correct key
- **Fix**: Always verify localStorage key names against source before querying them in console scripts

### 2. **`folderDropHighlight` ReferenceError (alpha.4 crash)**
- Added `setFolderDropHighlight('__trash__')` in the drag-to-Trash implementation
- `setFolderDropHighlight` is a DOM helper that takes an element reference (not a string ID)
- Also referenced `folderDropHighlight` state variable that doesn't exist
- App crashed immediately on test
- **Fix**: Read the function signature before calling it; `setFolderDropHighlight(e.currentTarget)` was correct

### 3. **`integrity.js` Not Committed on Initial Release Push**
- `integrity.js` was a new untracked file; the release commit only staged modified files
- Required a second commit to add the design doc and module
- **Fix**: Run `git status` before the release commit to catch untracked files that belong in the release

### 4. **Over-Engineered Timing Analysis for Post-Import Integrity Check**
- Spent significant analysis time trying to thread `mergedBooks` and `folders` through `loadLibrary`'s return value to run integrity check immediately after import
- The pending-flag pattern was simpler and more correct, and was available from the start
- **Fix**: When dealing with React async state, reach for the useEffect pattern first rather than trying to pass values explicitly

## 📚 Lessons Learned

### 1. **Homeless Books Are Always a Bug**
- By design, every non-deleted book must be in at least one folder — Inbox is the default
- Removing a book from its last folder is a delete operation
- Therefore homeless books (non-deleted, zero folder memberships) are always a structural violation — there is no legitimate user-reachable state that produces them intentionally
- This invalidated the "maybe intentional" counter-argument and justified auto-fix on load
- **Why this matters**: Integrity auto-fixes don't need user confirmation when the invariant has only one correct resolution

### 2. **The Three-Layer Race Condition Pattern**
The complete protection for single-user browser app data:
1. **Atomic transaction** — clear+add in single IndexedDB transaction (no intermediate empty state)
2. **Write mutex** — promise chain serializes concurrent callers (45+ fire-and-forget saves queue safely)
3. **Operation guard** — ref prevents overlapping high-level operations (import, restore, delete, device-state push)
Each layer catches what the others miss. All three are needed.

### 3. **Design Doc Reveals Cross-Cutting Causes**
- The individual incidents (Jan orphan wipe, Feb redo race, Mar tag wipe) looked unrelated in isolation
- Writing the incident timeline together revealed a single underlying theme: no structural guarantees on data operations
- This reframed "fix the bug" as "add a layer of protection that prevents the class of bugs"
- **Why this matters**: Systemic fixes are more valuable than point fixes; you need the timeline to see the system

### 4. **Virtual Folders vs Real Containers in UI**
- All Books and pinned tag views are read-only lenses; folders are writable containers
- Mixing them in the same visual hierarchy (current state) causes confusion about what can be modified
- The Views / My Library split is the architecturally correct separation — planned for a future release
- **Why this matters**: UI hierarchy should mirror semantic hierarchy; when they diverge, users get confused

## Final Thoughts

This release was unusual: it started from a data corruption incident whose exact trigger was never identified, and ended with a system that prevents the entire class of problems. The design doc approach was essential — writing the incident timeline from January through March revealed that every data integrity failure shared the same root causes. That reframe turned "fix the race condition that caused the March 6 corruption" into "add three structural layers that prevent all concurrent write races," plus a proactive integrity check that catches whatever slips through.

The 272 homeless books discovered during the investigation were a bonus find — historical debt from before Inbox placement logic existed, invisibly accumulating for months. They'll be silently fixed on first load for all users.

**Key Takeaway**: Systematic problems require systematic solutions. Writing the incident history together reveals patterns that individual bug fixes never expose.
