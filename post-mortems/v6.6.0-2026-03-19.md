## 🎯 What Worked Well

### 1. **Systematic console diagnostic for Inbox bug**
- Step-by-step isolation (restore → delete → permanent-delete → move) pinpointed the exact failure: books were removed from all folders but never added to Inbox.
- **Lesson**: For stateful UI bugs, a reproducible step sequence with state inspection at each step is far faster than code reading alone.

### 2. **`isBackupData` flag already existed in storage.js**
- The fix for backup restore → Trash was one conditional using an existing flag (`isBackupData = !!book.userEdited`) that was already used for `userEdited` merge but omitted for `isDeleted`.
- **Lesson**: When a bug involves a merge/conditional path, check whether the right discriminator already exists before designing a new one.

### 3. **UX reasoning before tooltip/toast copy**
- Discussing All Books / Trash behavior and the hardlink copy model before writing copy led to the right tooltip and toast phrasing the first time, rather than iterating on wording.
- **Lesson**: "UX expert hat" prompts produce better outcomes before any code is written, especially for mental model explanations.

## ❌ Mistakes Made

### 1. **Three failed attempts to fix Ctrl+Drag before finding the real root cause**
- **alpha.4**: Read `e.ctrlKey` from `onDrop` instead of `onDragOver` — still failed (`e.ctrlKey` unreliable in drop events too on Windows/Chrome).
- **alpha.6**: Global `keydown`/`keyup` listener for `ctrlKeyRef` — correctly detected Ctrl, but copy still acted as move.
- **alpha.8**: Root cause finally found — React's `setFolders` updater function is called *after* the event handler completes, so `explorerIsCopyDragRef.current` had already been reset to `false`. Fixed by capturing `const isCopy` before `setFolders`.
- **What should have been done**: After alpha.4 failed despite the toast showing correctly, the discrepancy between "toast fires with copy message" and "book still removed" should have immediately pointed to the `setFolders` timing issue. The toast firing correctly meant the ref was right; the removal meant the updater saw something different. That's a classic closure/ref timing bug.
- **Fix**: Capture copy state into a local `const isCopy` before any `setFolders` call. Never read a ref that resets inside a React state updater.

### 2. **`explorerIsCopyDragRef` inside `setFolders` updater — pre-existing latent bug**
- The pattern of reading `explorerIsCopyDragRef.current` *inside* `setFolders(prev => ...)` was present in three of the four drop handlers from the original implementation. It worked accidentally in cases where the ref wasn't reset before the updater ran, but was always technically incorrect.
- **What should have been done**: Any time a `useRef` value is read inside a React state updater, it should be captured into a local variable first.
- **Fix**: All three handlers now use `const isCopy = ctrlKeyRef.current` before `setFolders`.

### 3. **`e.ctrlKey` in drag events assumed reliable**
- Multiple rounds of fixes assumed `e.ctrlKey` would eventually be reliable in some drag event context. It isn't, on Windows/Chrome, for any drag event type.
- **What should have been done**: Recognized sooner that the entire drag API's modifier key support on Windows is unreliable and gone straight to the global listener approach.
- **Fix**: `ctrlKeyRef` via `window.addEventListener('keydown'/'keyup')`, completely independent of drag events.

## 📚 Lessons Learned

### 1. **React state updater functions run after the event handler**
In React 18, `setFoo(prev => ...)` schedules the update. The updater function is called during the next render batch, *after* the current synchronous event handler completes. Any `useRef` value read inside the updater reflects the ref's state at render time, not at the time `setFoo` was called.

```javascript
// WRONG — ref may be reset by the time updater runs
myRef.current = true;
setFoo(prev => {
    if (myRef.current) { ... }  // may see false
});
myRef.current = false;  // resets before updater runs

// CORRECT — capture before setFoo
const value = myRef.current;
setFoo(prev => {
    if (value) { ... }  // always sees true
});
myRef.current = false;
```

### 2. **Windows/Chrome drag API modifier keys are unreliable**
`e.ctrlKey`, `e.shiftKey`, `e.altKey` in `dragstart`, `dragover`, `dragenter`, and `drop` events are not reliably populated on Windows/Chrome. The OS may intercept modifier+drag combinations before they reach the browser. The only reliable approach is global `keydown`/`keyup` listeners on `window`.

### 3. **`isBackupData` discriminator should apply to ALL fields that shouldn't merge from IndexedDB**
The `isBackupData = !!book.userEdited` check in `storage.js` was designed to prevent Amazon import data from overwriting user-edited metadata. The same logic applies to `isDeleted`, `deletedAt`, and `deletedFromFolderIds` — backup files represent the user's intended state and should always win on restore, not OR-merge with whatever IndexedDB contains.

### 4. **All Books should exclude Trash — UX mental model matters**
Including deleted books in All Books (even with a badge) violates the user's expectation that deleting a book removes it from their library. Every app with a Trash model (Finder, Gmail, Photos) excludes deleted items from all non-Trash views immediately. The count and the view must be consistent.

## 💡 Recommendations for Future

### 1. **Audit all `useRef` reads inside `setFoo(prev => ...)` updaters**
This codebase has many state updaters. Any that read a ref whose value could change by end of event handler are potential bugs. A grep for `Ref.current` inside `setFoo(prev =>` would be a useful one-time audit.

### 2. **Test Ctrl+Drag on Windows specifically for any new drag feature**
Windows/Chrome drag API quirks affect modifier key detection. Any new drag feature should be tested on Windows before release, and modifier key state should always use `ctrlKeyRef` (global listener), never `e.ctrlKey` in drag events.

## Final Thoughts

This release fixed five bugs, three of which were in the same feature (Ctrl+Drag copy). The copy bug required three separate attempts because each fix addressed a real problem but exposed the next layer underneath: unreliable `onDragOver` modifier key → unreliable `onDrop` modifier key → React updater timing. The final root cause (React `setFoo` updater timing) is a subtle but fundamental React pattern that applies broadly across the codebase and warrants a one-time audit.

**Key Takeaway**: Never read a `useRef` inside a React state updater — capture the value into a local `const` before calling `setFoo`, or the ref may reflect state from a later point in the event handler rather than the moment of the call.
