**Date**: 2026-06-07
**Duration**: ~5 hours, single session
**Versions Iterated**: 5 alphas across two releases (6.11.7-alpha.1 through alpha.4 + 6.11.8-alpha.1)

Two releases, one logical thread. Started with a Tags-filter UX asymmetry, ended with the Tags-filter UX asymmetry. Almost shipped without fixing it.

## 🎯 The Arc

Ron tried to record Tutorial 1 Scene 6 (Tags & Views) and hit a UX wart: the Tags filter dropdown's empty state showed "No tags available" with no path to create one — forcing a navigation to View → Manage Tags before recording could continue.

We discussed, evaluated, agreed it was a real UX bug, and recommended fixing it. Then — without writing the fix — the conversation branched:

1. *"Does Collections have the same issue?"* → investigated, no (no editable concept exists). Side observation: Collections lacks an explanatory tooltip.
2. *"Wait, these other filters all lack tooltips too"* → Ron requested tooltip proposals for 4 controls. Added.
3. *"Page Unresponsive on hard refresh"* → diagnosed, added a folksy splash banner.
4. *"Tooltips are too long as single lines"* → multi-line formatting.
5. **Released 6.11.7.**
6. *"We never fixed the first thing that started all this."*
7. **Released 6.11.8.**

## ✅ What Worked Well

### 1. **The morning's PM synthesis informed afternoon decisions**
This morning we wrote `feedback_alpha_testing.md` after the v6.11.6 "tested alpha against prod" mistake. This afternoon, every single spot-check direction explicitly sent Ron to `python -m http.server 8000` and `localhost:8000`. The memory-to-action chain worked: we identified a recurring pattern, encoded it, and immediately stopped repeating it. That's the whole point of the memory system, demonstrated in one day.

### 2. **ffprobe verification answered "what tool did I use" definitively**
Ron didn't remember whether scenes 1-5 were shot with OBS or Snipping Tool. Rather than speculate or ask him to dig through file history, one ffprobe call on `scene-1a.mp4` revealed: 1906×1074 (non-spec resolution), 30fps (not the spec'd 60), `AVC Coding` encoder tag — three converging signals for Snipping Tool. Production guide updated to match reality.

### 3. **Asked-then-waited for design questions**
When proposing tooltip text and splash banner copy, I gave Ron labeled options (A/B/C) with my lean and the tradeoff for each. He picked, I implemented. The new `feedback_wait_for_answer` memory was honored throughout — no lurching forward on guessed answers, even when the changes were small.

### 4. **Chrome "Page Unresponsive" diagnosis was honest**
Ron asked for "an easy multi-step load trick or something." The honest answer is that there isn't one short of precompiling Babel — and I said so rather than offering noise. We landed on the banner: doesn't suppress the dialog, but reframes it as expected behavior. Set expectations rather than chase the unsuppressible.

## ❌ Mistakes Made

### 1. **Original issue buried for ~4 hours — almost shipped without it**
This is the headline mistake of the session, and it's a textbook instance of the *"Recommendations for Future" recur-without-doing* pattern flagged in this morning's PM synthesis. The arc:
- 12:30 — Tags asymmetry discussed, "Recommend: fix it."
- 12:35 — branched to Collections investigation
- 12:50 — branched to tooltip proposals
- 13:30 — branched to splash banner
- 14:20 — branched to multi-line tooltips
- 15:00 — released 6.11.7. **Original issue still unfixed.**
- 15:25 — Ron: "We never fixed the first thing that started all this."

Each branch was legitimate work that touched related UX surfaces. None of them was wrong individually. But cumulatively they buried the original task, and **the safeguard that finally caught it was Ron's memory, not the workflow**. The synthesis I wrote this morning called out this exact pattern as a top-three recurring failure. Within hours, we ran the live demo of it.
- **Lesson**: When a discussion confirms "Recommend: fix it" and then immediately branches to a related concern, **the recommendation needs an explicit anchor before the branch happens** — a TodoWrite entry, an in-conversation tag like "(parked: Tags empty state, will return)", or a refusal to discuss anything new until the original fix is filed. The discussion-confirms-fix step is not a fix.

### 2. **Banner placement chosen without considering Chrome dialog overlap**
First banner attempt at `top:24px` was directly behind Chrome's "Page Unresponsive" dialog. Took alpha.3 to move it to `25vh` after Ron's screenshot. The Chrome dialog is reliably near the top of the viewport — I knew this when I picked the location, and still picked the location it covered. Should have asked Ron's intended placement before alpha.1, or anticipated the overlap from first principles. Cost: one alpha and one screenshot round-trip.

### 3. **"Sizzle Reel needs slow-mo" conflation**
Stated as fact that the Sizzle Reel needed 60fps for slow-motion, then Ron correctly pointed out the shot list doesn't mention slow-motion anywhere. I had conflated "CapCut/DaVinci supports speed-ramp" (general capability) with "this video uses speed-ramp" (specific requirement). Same shape as the v6.11.5 "Amazon Insider speculation" mistake — reaching for inference instead of verification.
- **Lesson**: When making claims about what a video/feature/script *requires*, verify against the actual document, not what you remember the capability is.

## 🔗 Follow-Up Items

1. **TODO.md 7d added: tooltip inventory audit** (LOW/LOW, 1-2h). The 4 tooltips we added were found by chance during one scene's prep. A systematic walk through every toolbar, dropdown, badge, and icon button across desktop + mobile would catch the rest pre-launch.

2. **The drift pattern needs a process-level guardrail.** A single new feedback memory entry probably won't fix this since [[feedback_wait_for_answer]] already addresses adjacent ground. Better candidates: a TodoWrite discipline ("any UX bug confirmed during discussion gets filed before the conversation branches"), or a meta-rule encoded into the PM template that asks "did anything from this session get raised, agreed, and not done?" Worth thinking about; not worth blocking videos to design today.

3. **The Chrome "Page Unresponsive" mechanics finding** is worth keeping. Quoted from this session: the dialog fires when *user input queues without response*, not on a fixed-duration block. CSS animations on the compositor continue and look fine; the dialog can be triggered or silent for the same load profile depending purely on whether the user clicked. Not memory-worthy on its own — but worth knowing if precompile gets prioritized.

4. **Sizzle Reel & Scene 6/7 still pending.** Ron stated "first thing tomorrow." That's the open thread. Production guide is now accurate to reality (Snipping Tool + DaVinci, TBD on sizzle tool), so future-Ron has correct breadcrumbs after the next break.
