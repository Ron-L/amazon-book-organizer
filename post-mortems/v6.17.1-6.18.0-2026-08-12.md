**Date**: 2026-08-12
**Releases (all prod + dev, clean fast-forwards)**:
- **6.17.1** (`7fbb969`) — sync-corruption recovery dialog + `docs/design/DATA-DURABILITY.md`
- **6.17.2** (`e58a0c0`) — import summary reports ownership upgrades ("N now owned")
- **6.18.0** (`311adf4`) — Book List & tag refinements (#2 keep-selection, #4 selectable context covers, smart-name-everywhere, #3 Select All in Tags, #5 drag-to-order tags)

This PM leans deliberately on **process/performance**, because that's what needed examining — Ron's words: *"I kept having to surface stuff and other issue with your performance."* He was right.

---

## ✅ What worked well
- **The durability decision got captured, not just made.** `DATA-DURABILITY.md` records *why* wishlist stays (RW-only vs Amazon-recoverable, the atomic-commit relationship, the catalog-beyond-Kindle scope) so it can't be re-litigated from scratch.
- **Reconcile-merges stayed clean.** Three concurrent branches off `6.17.0`; each release merged `main` in first, and every conflict was the single `ORGANIZER_VERSION` line. Never force-pushed.
- **A safe test hook** (`window.RW_FORCE_CORRUPTION`) let Ron exercise the corruption dialog without corrupting the relay — deterministic, non-destructive, then stripped at release.
- **The engine + unit tests** stayed green throughout (16 tests) and anchored the consolidate work that preceded this.

## ❌ What went wrong (the pattern)
Four recurring failures, all the same shape — **I substituted assumption/partial work for verification, and left Ron to catch the gaps:**

1. **Reasoned from a wrong mental model instead of the code.** I treated **RW Wishlist** (RW-native records scraped from Amazon product pages → relay+local only) as the **Amazon account wishlist** (Amazon-durable), and built a whole keep-vs-eliminate *durability* argument on that false premise. Ron corrected me **twice** and told me to go read the code before I got it right. → new memory **[[feedback_verify_dont_assume]]**.
2. **Investigated only what Ron had personally hit.** I wired the corruption message into the surfaces he'd seen and called it done; he had to prompt *"do a search and ensure all bases are covered."* One grep of `RWRelay.download()` callers would have answered it up front. → new memory **[[feedback_investigate_completely]]**.
3. **Mis-executed locally-untestable UI.** (a) The corruption flow showed **two** dialogs (a leftover `progress.finish` + the real one) — I should have traced it. (b) #5 made the whole **`<tr>` draggable**, a known-flaky pattern that just selects text; the fix was a **grip handle**. Both needed Ron to diagnose.
4. **Misread literal instructions.** I inverted "there's **no** reason it needs to be a **new** tab" into "it **must** be a new tab," twice.

**Root cause:** long-session context drift + optimism. When a model felt hazy I *opined* instead of *re-reading*; when a task was "handle X everywhere" I did the visible subset. Both are cheap to avoid (grep/read first) and expensive when the user has to correct them.

## 📚 Corrections applied (memory)
- **[[feedback_verify_dont_assume]]** — re-ground in the code before opining on an existing behavior/model; a hazy model is the signal to re-read, not to guess.
- **[[feedback_investigate_completely]]** — enumerate ALL instances of a class (call sites, error paths, surfaces) up front and present the map; don't make the user surface the rest.
- Reinforces existing **[[feedback_verify_live_handler]]** and **[[feedback_debugging]]**.

Two more, not worth their own memory but noted: for untestable UI, apply known pitfalls (draggable table rows are unreliable → use a handle) and trace the interaction before shipping; and read the user's *literal* words, re-reading on correction rather than re-applying the assumption.

## 🔧 Process notes
- **Concurrent-branch version numbers are speculative.** Three branches each claimed a number; the real numbers were assigned at release in merge order (6.17.1 → 6.17.2 → 6.18.0), with the losers renumbered. Worked, but next time consider serializing releases or leaving the version bump to release time to reduce churn.
- **Skipped PMs on 6.17.1 and 6.17.2** — this consolidated PM covers them. Don't let small-but-substantive releases skip the retrospective.

## Final thought
The features landed and are coherent; the *way* they landed cost Ron too many corrections. The fix isn't "try harder" — it's a concrete habit: **verify before opining, and enumerate before claiming done.** Those two are now in memory.
