## 🎯 What Worked Well

### 1. **Design-doc-first, then read-the-risky-step, then build**
- The user asked for a doc + plan before code. We wrote `docs/design/AUTO-ORGANIZE-SCOPE.md`, and — crucially — **read the "meaty" step before planning around it.** The plan called step 3 (source move-out) "the meaty bit… assume a rewrite." The read showed `computeOrganizePlan` *already* emitted a `REMOVE_BOOKS_FROM_FOLDER` subaction (hardcoded to `__inbox__`) and undo was already generic by `folderId`. So the "rewrite" was a **one-line parameterization**.
- **Lesson (reinforced)**: confirm the mechanism exists before you scope the work. Reading first turned the scariest step into the smallest.

### 2. **The de-organize guard came from war-gaming an edge, pre-build**
- The guard exists because the user probed *"what if I'm standing inside Mark Twain / Tom Sawyer and pick By Author?"* — which would flatten the series subfolder. We caught it in **design**, not production. The resulting rule ("skip any destination that is the source folder or an ancestor of it") is purely structural (parentId walk) — no folder "types" needed.
- **Lesson**: critically evaluating edge cases during design is cheaper than shipping a footgun. A tool named *Auto-Organize* silently offering to dis-organize would have been a bad surprise.

### 3. **Pure engine + unit tests carried the tricky logic**
- The two non-trivial pieces (parameterized move-out, the guard) live in the pure `organizeEngine.js`. Three new unit tests (source-move-out, flatten-guard, deepen-allowed) proved them without a browser — 11/11 throughout. The React wiring was then just plumbing.

### 4. **Incremental alphas + the user's hands-on testing caught the copy/UX issues**
- alpha.1 core → alpha.2 title → alpha.3 "Folder" wording → alpha.4 menu-gate + ordering. Each was a small, reviewable unit the user exercised, and *his* testing surfaced the real polish (hardcoded "Inbox" copy, folder-name ambiguity, series-first ordering) before release.

### 5. **Clean release**
- Divergence pre-flight (again): prod/dev exactly behind, zero prod-only commits → fast-forward, verified not assumed. CSS untouched → cache-buster correctly left alone.

## ❌ Mistakes Made

### 1. **Scoped the logic but left user-facing copy hardcoded to "Inbox"**
- alpha.1 changed the *gathering* to be folder-scoped but left the dialog body reading "These leave the Inbox" (and the title unscoped). I flagged the *title* as "step 5, pending" — but the **body copy is the same concern** and I hadn't scoped it. The user had to point at "Inbox" in a screenshot.
- **What should have happened**: when you scope a behavior, scope **every user-facing surface that describes it** in the same pass — logic and copy are one change, not two.

### 2. **Injected a bare folder name into copy without labeling it**
- alpha.2 rendered the scope as "Auto-Organize 'Collections'…". The user rightly noted a folder named like an RW term ("Collections", or literally "Book List") reads as a *keyword*, not a folder. alpha.3 fixed it to **"Collections" Folder** / **the "Collections" folder**.
- **Lesson**: when user data goes into UI prose, **label its role** ("X" Folder) so it can't be misread as a system term.

### 3. **Mis-remembered whether All Books was intentionally blocked**
- The user asked why All Books lets you Auto-Organize "which I thought was guarded." I had to reconstruct the distinction (the guard is a *flatten* guard; All Books → unfiled = nothing to de-organize). No harm, but a beat of "is this a bug?" that a clearer mental model would have pre-empted.

---

## 📚 Lessons Learned

### 1. **Scope logic and copy together**
- A behavior change and the words that describe it are one unit. Don't ship scoped logic with hardcoded copy from the old assumption.

### 2. **Label injected user data in UI prose**
- "X" Folder, not bare "X" — cheap insurance against a name colliding with a system term.

### 3. **Read the risky step before estimating it**
- The move-out looked like a rewrite and was a parameterization. One read reframed the whole plan's risk.

### 4. **Structural rules beat type-flags**
- The guard needed no "this is an author folder" metadata — a parentId same-or-ancestor walk answered "would this de-organize?" from structure alone. Less state, fewer ways to drift.

## Final Thoughts

A tight, well-scoped feature that started from a single frustration ("Auto-Organize doesn't work on wishlist items") and, through design-first discipline, turned into a coherent re-scoping with a genuinely valuable safety guard. The engine work was smaller than feared because we read before estimating; the guard was better than the default because we war-gamed an edge in design. The rough edges were all copy/UX, all caught by the user's hands-on testing before release.

**Key Takeaway**: When you change what an action *does*, change every surface that *describes* it in the same pass — and read the scary step before you budget it; it's often already half-built.
