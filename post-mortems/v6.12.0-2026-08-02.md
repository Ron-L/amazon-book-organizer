# v6.12.0 Release Post-Mortem — The Big One, the Data-Loss Root-Cause, and the Hotfix That Almost Vanished

**Date**: 2026-08-02
**Duration**: single session (mobile polish → data-loss fix → two bug fixes → release)
**Versions Iterated**: mobile 1.6.9 → 1.6.10; desktop 6.12.0-alpha.88 → alpha.93 (6 alphas), then **6.12.0**
**Release Components**:
- readerwrangler.js ORGANIZER_VERSION → 6.12.0
- readerwrangler.html APP_VERSION → 6.12.0 + CSS cache-buster → 6.12.0
- index.html softwareVersion → 6.12.0
- CHANGELOG.md, README.md, features.html
- mobile.js MOBILE_VERSION 1.6.10; amazon-library-fetcher.js FETCHER_VERSION v4.11.10

The largest release to date — **147 commits**: the ground-up Searches / Book Lists / Folders redesign, the unified folder-ordering model, and a full mobile visual refresh. This session was the tail end: it turned a frightening data-loss report into a structural fix, cleared two pre-release regressions, and then discovered at merge time that prod had quietly moved on without us.

---

## 🎯 The Arc

1. **Mobile polish** — drawer collapse-all + Dashboard per-shelf collapse → mobile 1.6.10.
2. **"Rebooted, lost ALL my Book Lists."** Investigated the two backups: `bookLists` was genuinely empty, while folders (184) and searches (3) survived. Root cause: **Book Lists had a single, unguarded persistence lifeline** (a standalone key + an unguarded save-effect that wrote `[]` on mount, plus a restore gated behind `books.length>0`); folders survived the same cold-boot race only because they were **double-stored** in the guarded organization blob. Fixed by making `bookLists` a first-class citizen of that guarded blob (alpha.88). The `Persistence-Field-Audit` doc's **finding F2 had literally predicted this trap.**
3. **A genuinely deep architecture conversation** — localStorage vs IndexedDB, synchronous vs asynchronous, the JS event loop and "ticks," React effect closures. Ron pushed to understand *why* before approving, and we converged on the key insight: **the guard (writer refuses to save before load completes), not the consolidation, is the safety mechanism.**
4. **Two pre-release bugs.** (a) Dragging a book folder→folder *copied* — a **stuck Ctrl ref**: the browser swallows `keyup` during a native drag, so a Ctrl released mid-drag stranded the flag into the next drag. Found via debug logging + the console's "28×" auto-repeat badge on `Ctrl DOWN`. Fixed by clearing the flag on `dragend`/`blur` (alpha.90). (b) A multi-select menu "Move to" that *sometimes* copied — instrumented, and **Ron reproduced it as a hover slip (user error)**, so we shipped no fix. Then (c) the **Series-secondary sort regression**: the v6.12.0 compound `series` comparator resolved within-series order internally, so an explicit `#` secondary was never consulted. Fixed with a precedence rule (alpha.93).
5. **The release.** Ran the checklist, bumped versions, finalized CHANGELOG/README/features. Then the merge to `main` **refused to fast-forward** — prod had **7 divergent commits**, including **Release 6.11.10, the Babel-8 hotfix that pinned `@babel/standalone` to 7.29.7**. Reconciliation merge, careful conflict resolution across 5 files, pushed prod + dev.

## ✅ What Worked Well

### 1. STOP-and-root-cause on the data loss
Rather than patch symptoms, we chased the structural cause and found the exact asymmetry: Book Lists were the *one* piece of irreplaceable organization with a single, unguarded lifeline. The fix wasn't a special case — it made Book Lists behave like the already-proven `savedSearches`. Root cause → matching an existing resilient pattern, not inventing new machinery.

### 2. The `--ff-only` guard caught the prod divergence
The release plan assumed a clean fast-forward. It wasn't — prod had a **production hotfix** the branch never saw. Because the merge used `--ff-only`, it **failed loudly instead of silently creating a surprise merge or (worse) tempting a force-push that would have dropped the Babel pin**. I stopped, investigated the 7 commits, confirmed the branch already carried the pin, and reconciled deliberately. "Check before pushing to prod" paid off exactly as designed.

### 3. Evidence over theory on the bugs
For the drag bug, I instrumented `ctrlKeyRef` and let the console *prove* the stuck flag (the auto-repeat "28×" badge with no matching `Ctrl UP`). For the menu move→copy, I instrumented the shared submenu state and let Ron reproduce it — which revealed it as a user-error slip, sparing an unneeded fix. Both times the logs, not a theory, decided it.

### 4. Honest retraction
During the release survey I flagged a "Moved N books to 'List'" toast as misleading. On reading the *full* handler I found it fires only for Book-List→Book-List drags (which genuinely are moves); folder→list already says "Added." I said so plainly and made **no spurious edit**, even though we'd already "agreed on wording."

### 5. Mutual UX correction on the sort fix
I talked Ron off option #3 (orthogonality would break the most common "sort by Series" case); Ron talked me off #1 (his "what if only the Series column is visible?" scenario exposed a real discoverability trap). We landed on #2, reframed as a clean precedence rule — a better answer than either of us started with.

## ❌ Mistakes Made

### 1. Release plan assumed a clean fast-forward — didn't check divergence in pre-flight
I laid out the entire "fast-forward `main` → push prod" plan without verifying the branch's relationship to the release target. The 7 divergent prod commits (including a hotfix) only surfaced when `--ff-only` aborted mid-release. It ended safely, but the discovery should have happened during pre-flight, not mid-merge.
- **Lesson**: For a long-lived feature branch, **check divergence from the release target (`git log branch..main`, `git rev-list --count HEAD..main`) as part of pre-flight** — prod may have accumulated hotfixes. Draft the merge/push steps *after* confirming the actual shape.

### 2. Flagged a bug that wasn't one, from a grep line
I claimed the drag-to-Book-List toast said "Moved" (misleading) based on a `grep` hit, and we discussed and "agreed on wording" for a fix — before I'd read the surrounding handler that scoped "Moved" correctly to list→list. Pure inference-over-verification, the same shape as prior PM mistakes.
- **Lesson**: **Read the full handler before proposing a fix**, not the grep line that mentions the string.

### 3. The data-loss trap was predicted — and shipped anyway
`Persistence-Field-Audit` F2 (written 2026-06) said, verbatim, *"the asymmetry with folders is a trap. Today it's saved by its own effect, so OK…"*. It was **not** OK — it cost Ron every Book List on a reboot. An audit item explicitly labeled a **trap** but rated "OK for now" is a latent incident, not a note.
- **Lesson**: When an audit flags an asymmetry as a "trap," that's a **fix-before-it-springs**, not a deferred observation. "OK today" + "trap" = schedule the fix.
