## 🎯 What Worked Well

### 1. **Architect discussion before implementation**
- Before writing any code, we discussed two options: (a) clean on backup export, (b) clean on folder delete with undo preservation. The backup-export approach was ruled out because it would mean undoing past a backup export could silently lose sort settings — surprising to users.
- **Lesson**: A two-minute architecture discussion eliminated a whole class of subtle undo bugs before writing a line.

### 2. **Single alpha, clean release**
- Root cause was clear (no cleanup on delete), fix was targeted (5 edit sites), no unexpected interactions.
- **Lesson**: When the problem is well-understood before starting, implementations go cleanly.

---

## ❌ Mistakes Made

### 1. **Orphaned data accumulated silently for an unknown number of versions**
- `folderSortSettings` has been in the codebase since v5.0.0-alpha.100. Folder delete never cleaned it up. Every deleted folder left a permanent entry in localStorage and in backup files.
- **What should have been done**: Any time a state map is keyed by entity ID, the cleanup path (delete entity → remove key) should be implemented at the same time.
- **Fix**: Always pair "add to map" with "remove from map on entity delete."

---

## 📚 Lessons Learned

### 1. **Entity ID → state map cleanup must be paired with entity deletion**
Any `useState` map of the form `{ entityId: value }` needs a cleanup step wherever that entity can be deleted. In this codebase: `folderSortSettings`, `collapsedGroups`, and similar per-folder state. If the delete handler doesn't clean the map, orphaned entries accumulate indefinitely in localStorage and backup files.

Pattern to follow:
```javascript
// On entity delete — always clean related maps
setFolderSortSettings(prev => {
    const next = { ...prev };
    deletedEntities.forEach(e => delete next[e.id]);
    return next;
});
```

### 2. **Undo losslessness requires saving state in the action record**
When deleting an entity that owns state (sort settings, preferences, etc.), that state must be captured into the undo action record at delete time. Relying on the state still being present at undo time is wrong — the user may have reloaded, cleared storage, etc. Saving it in the action record makes undo self-contained.

### 3. **Backup-export cleanup is the wrong place for orphan removal**
Cleaning orphaned map entries on backup export (rather than on delete) was considered and rejected. Reason: backups represent a point-in-time snapshot. If the user restores a backup, they expect undo to work across the restore. If export had cleaned the orphans, undo records referencing those settings would silently lose their data. Clean at delete time; never rely on export to fix structural issues.

## 🔄 Rule Updates Made/Proposed

### New pattern to remember
- **Pair `setState` map additions with cleanup on entity delete.** Any `{ entityId: value }` map must have a corresponding delete path wherever that entity is removed. This applies to `folderSortSettings` (now fixed) and should be audited for other similar maps.

## Final Thoughts

A small, clean release. The bug was invisible to users (orphaned localStorage entries don't cause errors) but caused backup files to accumulate stale data — surfaced only when inspecting a demo backup file. The fix is straightforward; the more important outcome is the general pattern: always pair map additions with map cleanup on entity delete.

**Key Takeaway**: Any `{ entityId: value }` state map must clean up its entry wherever that entity is deleted — and if undo is supported, save the value in the undo record first.
