## 🎯 Trigger

User got a "Channel X was revoked by user" email from the relay alerts pipeline. Checked: not his channel — another ReaderWrangler user revoked theirs (different UUID lived in his testing-profile localStorage). The conversation turned to "I don't actually want individual emails for this at scale" — user-initiated revocations are normal lifecycle events, not security events. The original email-alerts design was written when Ron was the only user; every event mattered. At launch scale it's noise.

## ✅ What Worked Well

### 1. **Design-first conversation before code**
Asked two scoping questions before editing: (a) swap revoke→GoatCounter only, or take the opportunity to instrument the full lifecycle?, (b) update SECURITY.md to reflect the new policy? Both yes. That five-minute exchange prevented a "we only fixed the revoke and now the funnel is half-instrumented" follow-up. The whole 4-event funnel (created → used → revoked → blocked) shipped as one coherent unit.

### 2. **Pattern reuse for server-side telemetry**
The existing GoatCounter pattern is client-side `new Image().src = '...'`. Server-side calls from the Cloudflare Worker required a `fetch()` instead, but the same `/count?p=/event/<name>` endpoint and the same fire-and-forget try/catch wrapper. ~10 lines of new code (`fireGoatCounter` helper) that extend an established pattern rather than introduce a new one.

### 3. **First Cloudflare Worker deploy of this conversation**
The relay worker is separate infrastructure from the app, and we'd never deployed it via this assistance session before. The flow worked: `npm --prefix relay run deploy` from the user's interactive terminal (wrangler needs a browser auth flow we can't do from here). User got an OAuth tab, deploy completed in ~5 seconds, new version `edb8017d` live before the app release.

## ❌ Mistakes Made

### 1. **Told the user to test the alpha on prod**
Said "Hard-reload readerwrangler.com (Ctrl+Shift+R, cache-busted to ?v=6.11.6-alpha.1)" in the spot-check instructions. But readerwrangler.com is **prod**, and the alpha commit was never pushed — only local. So no amount of reloading would produce the new behavior. User correctly reported "Network tab is empty" and we had a multi-message detour to diagnose the wrong root cause (cache-busting) before reaching the right one (wrong environment entirely).
- **Lesson** — and this is the durable one: alpha testing happens locally (`python -m http.server 8000`), or after a dev push. Never against prod. The alpha workflow doesn't bump `APP_VERSION` (only `ORGANIZER_VERSION`), so the JS cache-buster query param stays the same, meaning even a hard-reload against prod returns the *deployed* code, not the local working copy. Wrote a memory entry to encode this.

### 2. **Cache-busting model was incomplete**
Even before the prod/local mistake above, my mental model of the alpha workflow was wrong. I assumed bumping `ORGANIZER_VERSION` was enough to identify the build. It's enough to *log* it, but not to *serve* it — the HTML loads `readerwrangler.js?v=${APP_VERSION}` and `APP_VERSION` is fixed at the previous release until the new release. This is intentional (avoids cache churn during development) but means in-place upgrades silently miss the alpha unless you hard-reload or disable cache.

### 3. **Initial deploy attempt hit auth wall**
Ran `npm --prefix relay run deploy` from the non-interactive shell. Wrangler refused — non-interactive mode needs `CLOUDFLARE_API_TOKEN` env var. Could have anticipated this and asked the user to deploy from his terminal as the first step. Cost: one failed-deploy message round-trip.
- **Lesson**: For tools that require browser-based OAuth (wrangler, gh auth, etc.), default to "ask the user to run it" rather than trying first.

## 🏗️ Technical Debt Flagged

**Permanent KV growth from `lifecycle:{channelId}:used`** — Every channel that ever uploads a manifest now gets a permanent KV entry that never expires. At current scale (single-digit users) this is irrelevant; at launch scale (hundreds-to-thousands), it's still under 1 MB total because each value is just an ISO timestamp. But there's a soft Cloudflare KV storage limit (free tier: 1 GB) and any permanent-keys-per-user pattern compounds. Not a problem today; worth noting if the user count gets serious.

**Email alerts pathway is now narrower** — Only auto-blocks email. If the auto-block code path ever silently breaks (e.g., the rate-limit check regresses), abuse could go undetected. The GoatCounter `relay-channel-blocked` event provides a redundancy signal, but only if Ron checks the dashboard. Consider adding a smoke-test alert (e.g., weekly "all systems normal" email) if email becomes the only abuse channel.
